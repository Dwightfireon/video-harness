# 制作性能审查与优化 · 2026-10-26

## 结论

这次耗时主要不是编码器本身慢，而是**制作时反复整片渲染、增量路径被关闭、帧缓存被主动删除，以及重复准备/质检**。单次出片速度与制作总耗时必须分开看。本轮修复了可独立验证的路径，没有降低分辨率、帧质量或质量门槛。

没有恢复、修改或重渲已删除的视频。旧项目只作只读取证；实际渲染验证使用自动清理的隔离合成工程，未调用付费模型或实际 TTS。

## 已落实

| 问题 | 修复与边界 | 位置 |
|---|---|---|
| Agent 的 render 阶段永远加 `--all` | 交由 CLI 自动判定，仍检查时间轴、共享输入、素材、编码与完整缓存 | `lib/agent.mjs` |
| `go` 成功后默认删除完整帧，下一次单场改动也整片重做 | 编辑期默认保留；显式 `--clean-frames`、`prune` 和发布后清理仍可用；会提示磁盘代价 | `vh.mjs` |
| Chrome 回退把参数数组展开成对象，丢 GPU/色彩/字体 flags | 新工程和实际渲染时精确修补项目副本、先备份、幂等；未知自定义代码不覆盖，不改全局 skill。升级后须建立新的整片基线，失败重试不能混用旧画面 | `lib/renderer-upgrade.mjs`、`vh.mjs` |
| 估算 build 后 measure 再生成同一份估算稿 | 对生成器及全部当前输入/生成 HTML 的内容指纹一致才复用；旧基线或任何变化仍重新生成。典型三次生成降为两次 | `vh.mjs` |
| 每个字幕首/中/尾采样都跨进程两次 | 每批最多 24 个探针，逐个等待异步 `renderAt` 再观察真实 DOM；普通/严格检查共享逻辑，保留完整覆盖与隐藏/截字检查 | `lib/subtitle-review.mjs`、`lib/subtitle-observation.mjs`、`lib/production-quality.mjs` |
| 对比度每个网格点单独调用 `getImageData` | 每张截图只取一次像素缓冲，采样坐标、众数和阈值不变；透明分组仍分别实测 | `lib/contrast-rendered.mjs` |
| 每份成片为了尺寸再启动一次 ffprobe | 同一次媒体探针供尺寸/流/时长判断使用；状态检查由两份媒体共 4 次探针降为 2 次，字节哈希与失败阻断保留 | `lib/artifact-status.mjs`、`lib/video-format.mjs` |
| 默认 4 路静默降为 1 路 | 显示默认降级原因、CPU/内存估计上限及系统报告空闲值；没有冒险上调并发 | `lib/render-budget.mjs` |
| 小数 FPS 在底层被 `parseInt` 截断，参数与缓存不一致 | 正式入口提前拒绝非整数 FPS，直到底层支持一致的小数帧率 | `lib/render-budget.mjs` |
| 制作 Agent 混用底层脚本、每改一个坐标就整片试版 | 仓库 `AGENTS.md` 明确统一入口、先静帧/预览集中修正、按失效原因最小重做，以及完整发布包要求 | `AGENTS.md` |

`--keep-frames` 保持兼容；保留帧会增加磁盘占用，不再声称“只保留分段也能安全增量”。全局 skill 脚手架仍含旧代码，但经本仓库 `vh new`/`vh render` 使用的项目副本会修复；绕过本仓库直接运行全局脚手架不在修复覆盖内。

## 实测

### 1. 字幕采样：同一份 90 句合成 HTML、270 个实际 DOM 探针

| | 优化前 | 优化后 |
|---|---:|---:|
| 本进程第一次调用 | 1425 ms | 806 ms |
| 第二次调用 | 605 ms | 467 ms |
| 第三次调用 | 未测 | 466 ms |

都是完整采样通过。第二次调用约缩短 **23%**；浏览器启动、系统缓存和负载有波动，不能把这个比例套给整片或整条制作流程。

### 2. 真实截图与编码：10 秒、5 场的隔离短片

固定 1920×1080、12fps、1 路、CRF 25；仅作为短合成基准，**没有把生产默认画质调成这些参数**。build 在每次作者修改后实际执行，表内计时仅包括 `vh render`，不含 build/TTS/混流。使用 `--force` 跳过合成工程不具备的旧人工清单，普通浏览器对比度/版式检查仍真实执行。

| 路径 | 命令总耗时 | 视频帧截图（不含质检截图） | 编码 |
|---|---:|---:|---|
| 首次渲染 | 5459 ms | 120 帧 | 新编 5 段 |
| 无修改再次 render | 1589 ms | 0 帧 | 跳过 renderer |
| 只改第 3 场后重建 | 3961 ms | 34 帧（含边界 padding） | 新编 3 段、复用 2 段 |

单场修改仍重编相邻边界段，这是当前 renderer 的正确性要求，不声称只编一段。无修改仍耗约 1.6 秒，说明重复浏览器检查尚有优化空间。

复现：`node scripts/benchmark-render.mjs diagnostics/performance-render-local.log`。脚本只操作自己创建的临时项目并在结束后清理，不访问用户作品。原始输出见 `diagnostics/performance-render-2026-10-26.log`。

### 3. 状态检查

旧项目只读 `artifactStatus()` 先前观测为 163–166 ms；本轮为 116/61/59 ms。样本少且有热缓存差异，不据此宣称固定提速比例。单独计数确认当前调用 2 次 ffprobe、同步读取 45,177,878 字节，旧版本为 4 次 ffprobe；仍读取媒体字节计算强指纹，没有靠跳过校验提速。

## 旧项目证据与不能直接放宽的守卫

回收站中的旧项目为 426.6 秒、12798 帧、16 场。持久状态记录 `--jobs 1 --fast --all`。本机 bundled Chrome 缺失、系统 Chrome 存在，确实需要回退路径。项目保存时缺增量缓存，但删除操作也会清缓存，不能仅据此认定制作时何时丢失缓存。没有保留完整分阶段日志，不能精确分解此前所述的 300–390 秒。

本机 16 GiB/10 CPU，一次预算观测的系统空闲内存仅约 232 MiB，因此被降到 1 路。macOS 的 inactive/可回收内存不等于 `os.freemem()`，也不能全部直接计入并发预算；本轮先暴露降级，未根据 CPU 核数硬开多路。已有内存压力时增加并发反而可能更慢。

**追加广告、口播时长改变还不能直接复用原片前缀。** 当前烧录进度条依赖 `t / DURATION`，改总时长会改变旧画面像素；字幕、切点、场数和跨场动画也会变化。本轮保留时长/切点/完整帧守卫，没有修改指纹或回执冒充缓存有效。

## 后续按收益排序的工作

1. **质检证据复用。** build、普通 render、严格 pre-render/final 仍重复启动浏览器与采样；普通 render 无改动也先检查后跳过。需拆开浏览器证据和最终媒体证据，按源码/素材、观察器与策略版本、浏览器及字体环境绑定；不能用 TTL/mtime 或旧失败报告放行。旧项目单轮严格浏览器检查约 550 个版式、267 个字幕探针，另有对比度截图。
2. **共享 helper 与检查器对齐。** 标题 `line()` 的 reveal mask 被当作持久截字；`frame()` 默认来源文字 y=896 与安全线约 y=860 冲突。需要修 helper 的稳定态布局并记录受信任的 reveal 区间，而不是全局取消裁切或豁免来源文字。
3. **元素级可读性覆盖。** 场内 55%/85% 的对比度探针不等于每个元素的停稳时间。旧稿末场有接近场尾才开始的 reveal；需要检查是否存在足够的完整可读停留，不能简单忽略低透明度。
4. **语义化测量与分场依赖。** 目前改非口播脚本 metadata 也可能重测；整个 SUBS 或 transition table 变化会扩大失效。需独立记录口播/分组/音色/速度身份，给字幕/转场建立局部依赖；真正共享 tail 仍需全局保护。
5. **状态轮询搬离强同步核验。** 轮询仍可能读几十 MB 媒体和阻塞 HTTP 事件循环。可推广已有 `production-view` 的轻量状态＋worker 强核验模式，未验证必须明确显示，交付前继续强检查。
6. **渲染器与 TTS 深层优化。** 分离全局 overlay、统一边界段与截图区间、支持离散场区间；截图后尽早释放 Chromium，再评估有界编码并发。TTS 应在第一个句缓存 miss 时才加载模型。先测工作集和 macOS 内存压力，不盲目把 1 路改成 4 路。
7. **诊断绑定当前输入并汇总所有失败类别。** 普通对比度失败报告会残留且提前阻断，可能让修完一种问题后才看到另一种。应保留完整证据、标识版本，并区分过期报告和当前失败，减少无效修复回合。
8. **统一场景解析与影响范围。** 部分路径直接按正则抓 `addScene`，会误计注释里的数字示例；逐场 body 又按相邻调用起点切片，把注释或全局 tail 归入前一场。需在状态、缓存、renderer 一起统一，不只改一层。所有素材合并成全局依赖、离散 `--scenes 2,15` 变成大连续区间，也会扩大重做范围。

以上不是已经完成的性能保证。此轮没有做持久质检缓存、场景缓存架构重构、全量轮询改造或 TTS 全命中启动优化。
