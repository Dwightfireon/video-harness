# 性能优化 · 2026-11-05（对比度采样与配音并发）

> 证据脚本、原始输出与旧模块副本见 `diagnostics/perf-2026-11-05/`。
> 所有数字都是本机实测；未取得的收益与已撤销的改动都写在下面，不把局部收益冒充整片提速。

## 1. 先看真实账

用 `vh performance` 与真实项目（10 场 / 178 句 / 730 秒成片）的阶段归因：

| 阶段 | 实测 |
|---|---|
| 配音合成（串行） | 236.5 s，178 句，每句约 1.3–1.4 s 几乎全是网络等待 |
| `vh quality` | 12.95–13.13 s |
| 其中对比度采样 | 5.10–5.42 s（20 个采样点，每点约 250 ms 截图） |
| 其中布局批处理 | 1.37 s（940 个探针） |
| 渲染截图 | 32.1 ms/帧；`renderAt` 本身 0.5 ms/帧 |

结论：真正的墙钟开销来自**等待**（配音网络往返）与**整页截图编码**（对比度采样），
不是 JS 计算。渲染里 `renderAt` 只占截图耗时的 1.5%。

## 2. 已实施

### 2.1 对比度采样只截文字并集

`lib/contrast-rendered.mjs`：把每次采样的整页 PNG 换成「所有被测文字盒的并集 + 10px 余量」。

- 20 个采样点：5096 ms → 2828 ms（**1.80×**），编码字节 23.7 MB → 12.1 MB（−49%）
- `vh quality`：13.1 s → 11.6 s（**−11%**），检查项与采样数完全不变
- 范围不可靠（坐标为负、超过视口、空集）时回退整页，不产生空裁剪

等价性证据：合成临界场景（渐变背景、45% 透明分组、近白文字、贴边文字、底部文字）
的三处失败项在元素、字色、采样底色、对比度上完全一致；另有四边贴边、滚动长页、
单个 12 px 小盒三个边界场景也完全一致。

### 2.2 edge-tts 并发合成

`scripts/voice-edge-tts-patch.py` 生成「未命中缓存的句子并发请求 → 按原句序转码写缓存」的脚本；
`vh.mjs` 默认传 `--tts-concurrency 4`；`lib/voice-script.mjs` 只对真正声明了该参数的脚本传参。

- 178 句真实项目：236.5 s → 59.9 s（**3.95×**）；并发 8 时为 31.7 s（**7.1×**）
- `timing.json` 的 subs / scenes / dur 逐项相同
- 178 个逐句 WAV 的 SHA-256 汇总相同
- `--tts-concurrency 1` 复现串行行为（226 s），可随时回退

失败语义未放宽：任一句失败不能产出有效测量或混流凭证；后续异常加固允许保存已成功的逐句缓存，续跑只补缺失句。缓存键、语速、音色、静音裁剪规则不变，见 [通用流程加固](pipeline-hardening-2026-11-05.md)。

## 3. 已撤销

### `captureBeyondViewport: false`

首轮同页连续测量显示截图 32.1 → 20.2 ms/帧，但那是测量顺序造成的缓存偏差。
改成交替重复、换到真实项目场景后：总耗时 7768 → 7704 ms（**1.008×**），截图阶段
6000 → 6000 ms（**1.00×**）。180 帧虽然逐字节相同，但**没有收益**，所以改动全部撤回，
迁移输出哈希与原模板一致。

这条记录的教训：同一浏览器会话内先跑 A 再跑 B，会把预热成本算到 A 头上。
凡是浏览器路径的 A/B，必须交替顺序并多轮取中位数。

### 媒体检查合并为单遍 ffmpeg

完整解码 5.4 s + 音频统计 0.36 s，合并后 5.55 s（**1.04×**）。视频解码占主导，
收益不足以抵消改动风险，未实施。

## 4. 测试与风险

- 全量 `npm test`：1457 通过 / 1 跳过 / 0 失败，与优化前基线一致。
- 新增 `test/voice-concurrency.test.mjs`：覆盖「只有声明了参数才算支持」「缺失脚本不误判」
  「注释里提到不算」。
- 对比度相关测试（像素读取次数、逐场采样证据、临界色判定）全部通过。

剩余风险：

- 并发合成的墙钟收益依赖网络往返延迟；对端限速、网络抖动或失败时可能比串行更慢，历史正常路径基准不提供速度下限保证。
- 裁剪采样依赖文字盒覆盖到所有被采样像素；代码在范围异常时回退整页，仍需在实际新项目上抽查。
- 未测量真实整片从 0 到交付的总耗时，上述都是阶段级数字。

## 5. 后续值得做

1. **布局探针的 `getComputedStyle` 复用**：每个探针约 710 次调用、2.6 ms；同一帧内
   同一元素会被重复查询样式。合并为一次遍历可再省一部分，但需要重写观察器并重新验证
   全部版式判据，风险高于本轮。
2. **质量检查的两遍媒体解码**：只有在同时需要完整解码与音频统计时才有 4% 收益，
   可以做，但优先级低于上面两条。
3. **渲染截图的真实热点**：若继续优化，应先分离 Chrome 的编码与合成耗时，
   不要从 `captureBeyondViewport` 这类参数猜测。
