# 问题优先的选题发现

## 目的

从“搜索值得改编的材料”调整为“发现值得问的问题，再调查依据”。材料可以启发问题，但可读网页和已有文章不再是问题候选的准入条件。

默认流程：

```text
方向、偏好、历史 → 提出问题 → 保存候选
                            ↓ 用户点击调查此题
                      检查前提、寻找材料与缺口
                            ↓ 用户确认
                        加入现有制作队列
```

不增加默认评分、独立审稿、多版比稿或自动付费重试。提出问题仍使用已配置模型，不是无成本的本地规则生成；默认不联网搜索材料，也不保证最新。

## 用户可见行为

- 候选先展示核心问题、为什么值得问、对谁有用和研究进度。
- 展开详情查看调查方向、待确认前提、研究发现、缺口与原文依据。
- 没有材料时仍能保存、收起、反馈、换角度、找子题；不能把无依据的新版问题直接送入制作队列。
- 调查只针对当前题，不受顶部未保存方向和每批数量干扰。
- 材料不足与前提需重构不是问题生成失败；仍保留原题，建议问法不静默替换它。
- 调查失败保留原题及此前成功取得的材料。刷新、轮询与断线恢复只读取已有任务，不重新提交调查。
- 新版问题的入队条件由服务端判定，界面只使用派生的 `canEnqueue`，不自行把来源链接数当作条件。
- 旧候选与队列不批量迁移，不补造依据，不自动重查。

## 数据契约

保留 `topic`、`subject`、`coreQuestion`、`why`、`outline`、`difference` 及已有流转字段，新增两个有版本的独立信息块：

```js
question: {
  version: 1,
  audience: '对谁有用',
  value: '为什么值得问，答案有什么理解或判断价值',
  investigate: ['调查方向一', '调查方向二'],
  premises: ['尚需确认的前提']
}

researchAssessment: {
  version: 1,
  status: 'unresearched', // 或 leads / insufficient / reframe
  finding: '',
  gaps: [],
  suggestedQuestion: ''
}
```

`candidate / queued / archived` 等仍表示用户操作和候选流转，不用它们承载研究进度。`leads` 表示取得可用线索，不是“答案正确”“事实已经证实”或“脚本已经完成”。实际原文仍由 `research` 保存。

新版问题必须同时满足研究状态和有效研究依据要求才能入队。旧记录缺少新版问题字段时兼容旧行为；不在只读接口中迁移写盘。

## 接口与边界

沿用异步任务和 HTTP 适配器，不让面板直接依赖队列 DOM、存储文件或模型实现：

```js
// 默认提出一批问题；换角度/找子题沿用 followupId、followup。
api.search({ query, mode, count });

// 仅调查一个现存问题。
api.search({ operation: 'research', topicId });
```

职责分离：

- 提示词负责问题价值与调查任务的编辑要求；不把这些主观要求伪装成机械质量评分。
- 纯问题规则负责字段规范化；材料规则负责工具记录、摘录与日期匹配。
- 执行器负责模型进程、超时、中断、输出上限和回收，不决定选题是否值得做。
- 编排层选择任务、合并最新状态和留档；记忆层负责反馈与入队事务。
- 中立的选题输入契约供发现和队列共同引用，避免制作队列依赖发现策略。
- `topicBrief()` 是制作输入的统一出口，将问题、未确认前提、依据和缺口交给后续写稿；不修改渲染、配音或发布链路。

文件边界：`lib/discovery-prompts.mjs` 只构造两种任务的提示词；`lib/topic-contract.mjs` 规范化共享数据；`lib/discovery-request.mjs` 解析请求范围；`lib/discovery-evidence.mjs` 校验原文；`lib/topic-research-store.mjs` 根据保存的真实工具记录判断新版问题能否入队。`lib/discovery.mjs` 负责执行与编排，`lib/topic-memory.mjs` 管理历史及显式反馈，制作队列只依赖共享数据契约。

资格检查不作为持久化的第二份真相：候选读取和入队时从现有记录派生。历史先筛选、分页，再读取本次实际返回记录的研究正文；同一回包只计算一次，下次读取仍能发现原文缺失或记录变化，不用永久缓存冒充有效。

## 自动化与资源边界

自动发现默认只提出问题。只有用户明确开启自动入队，才继续调查并将符合条件的问题入队。仍保留任务开始与结束时的开关检查、冷却、防重入、待选候选保护；手动操作永不因自动化开关而自动入队。

提出问题不要求网页证据，不使用“没读到原文”的网络看门狗；仍受总超时、输出大小、锁和进程生命周期保护。调查保留联网预算和原文规则。研究状态、材料校验、事实核实和制作完成是不同事情，不互相冒充。

## 验证方式

自动测试使用临时工作区、模拟模型/搜索结果及拦截的 HTTP 数据，不调用真实付费模型或搜索渠道。另用本机真实 OpenCode CLI 对接仅绑定回环地址的模拟模型服务，验证实际启动与配置继承：

- 后端验证无来源问题保存、独立调查、原文校验、失败保留、服务端入队门槛、自动化与旧数据兼容。
- 浏览器验证问题优先展示、按题请求、调查完成后的入队交接、材料不足与重构建议、失败不重发、历史与反馈回归。
- 真实 HTTP 与后台工作进程联调使用假模型事件，覆盖无来源生成、直接调用入队接口被拒、调查后人工入队，以及制作简报的交接；不是只测面板的模拟回包。
- 并发回归覆盖调查中手动入队、POST 未确认时读到旧终态、以及更早的 GET 在新 POST 确认后才返回。任务身份和请求代次独立于界面忙碌提示。
- 移动与桌面检查覆盖 320、375、768、1440 像素宽，无横向溢出。
- `out/question-first-validation/desktop.png`、`mobile.png` 是模拟数据界面预览，不是实际联网选题结果。

首次回归：16 个相关测试文件，179 项通过，日志在 `out/question-first-validation/final-tests.tap`。此轮只覆盖了模拟执行器，没有验证本机 CLI 与共享服务之间的配置边界，漏掉了下述启动故障。

启动修复后的回归：17 个相关测试文件，182 项通过，0 失败、0 取消、0 跳过。包含本机真实 CLI + 本地模拟模型服务、选题后端、两条真实 HTTP/工作进程联调、26 项面板浏览器用例、历史读取开销、旧队列和工作台布局；日志在 `out/question-first-validation/cli-fix-final-tests.tap`。未运行全仓库测试，未调用真实付费模型或搜索服务。

### 实际启动故障与修复

用户点击后立即显示 `opencode 退出 1`。用不存在的测试模型（不会计费）复现真实 CLI，发现标准输出中的 JSON 错误为 `Agent not found: "vh-questions-..."`：新临时 agent 放在子进程的 `OPENCODE_CONFIG_CONTENT`，但共享服务已经运行，不能继承这份环境。

- 存在运行期 inline 配置时使用 `--standalone`，由继承配置的私有服务运行；不写用户全局 agent、权限或凭证文件。
- 私有服务按所属进程组停止，不向共享服务发送私有会话的中断请求；共享调查任务继续保留原有会话中断保护。
- 退出码非零前先解析 stdout 尾部 JSON，连没有末尾换行的错误也保留；具体错误脱敏后才截断，不再只显示退出码。
- 新增真实本机 CLI 的回环模型测试；模型请求由本地模拟服务响应，不以真实付费调用充当默认测试。

自动化只能证明数据流与边界行为，不能证明模型一定提出好问题、来源真正支持解释或覆盖最新事件；实际选题质量需用户使用后判断。
