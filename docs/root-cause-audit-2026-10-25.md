# 自动制作反复中断：根因审查（2026-10-25）

## 结论

不是用户操作问题，也不能把这次事故归结为网络、额度或渲染器。

项目有可复用的媒体制作、版本核验和断点保存能力，但自动编排层仍依赖模型自行遵守大量文字指令；本地控制存在漏洞，失败恢复与测试验收也没有围绕真实交付闭环。这使不同输入不断触发同一类控制缺陷，表现为“每次都是一个新错误”。

当前准确定位是**需要熟练操作者介入的制作工作台**，不是已经验证可靠的无人值守产品。不必丢弃全部代码，但继续加提示词、计数器和单事故补丁不足以解决问题。

本轮是审查，不是修复完成声明。没有修改生产模块、原项目、凭证或质量阈值，没有恢复任务、调用真实模型、TTS 或重渲视频。只新增隔离诊断脚本和本报告。

## 1. 本次事故还原

项目：`projects/ChatGPT套餐怎么选-1025/`。

证据：`out/.vh-chat.log`、`out/.vh-task.json`、该任务的 `checkpoint.json`；任务 ID 为 `bc6ef554-826e-40ac-9196-1f871dab9ee2`。

- 自动制作已启用，内容修复使用次数为 0；不是耗尽“两轮修复”预算。
- 总计 44 个模型轮次。方案、7 场脚本和证据表已落盘；没有任何分场草稿。
- 写脚本时 `finish_draft` 被拒 4 次：一次缺主体字段，三次主体名称未与开场逐字匹配。这里的检查实际是字符串包含关系，不是语义核验。
- 进入 `draft_scenes` 后连续 12 轮读取/列目录，没有调用 `write_scene`。
- 第 8 轮起日志多次表示“本轮只能写”，但仍执行读取；还接收了一个 `run`，随后被命令安全策略拒绝。

- 早前有三次连接超时，均同渠道重试后继续；它们不是最终暂停原因。没有进入 build、TTS 或渲染，不能据此判断下游质量。

关键日志位置：`.vh-chat.log:177–236`；检查点保存 `turns=12, recon=12, offStage=4`。

## 2. 已确认的控制缺陷

### P0-A：普通首次输入被混同为“不可定向写入的新要求”

`vh.mjs:2275–2284` 会把首次文章正文传为 `instruction`。

`lib/agent.mjs:1190,1210` 以 `hasNewInstruction` 初始化 `sceneDirectionAllowed = false`。这不区分“按文章制作”与“先讨论、不要写入”；本次执行后面也没有在正常接收初始材料后重新开启。

结果：为保护用户插话而加的策略，关闭了正常首次制作所需的分场纠偏能力。长文章即便不登记修改契约，仍触发这个开关。

**整改方向：**把初始材料、制作授权、修改要求、只读要求和运行中插话分成明确类型；统一从任务范围计算授权，不在多个分支依赖一个粗粒度布尔值。只读/停止写入仍须优先，不能简单删除保护。

### P0-B：收窄工具只是请求建议，执行端没有同一份授权校验

`lib/agent.mjs:1807–1821` 收窄发给模型的工具；`1888–1963` 对返回调用只做“是否全局已知”和部分特殊阶段检查。没有通用地验证返回工具属于本轮 `requestSchemas`，也没有普遍强制本轮定向工具契约。

`performPending` 随后可按全局工具表执行调用。日志里“只能写”与实际读盘矛盾不是显示问题，而是执行约束未闭合。

这不代表所有安全保护都失效：写入模式、作者文件与命令仍各有守卫；也不能仅凭现有记录判断哪个上游组件忽略了工具列表。已能确定的是本地不应将上游守约当成前提。

**整改方向：**同一份阶段契约同时生成提示、工具列表和执行授权；执行前校验工具、参数、目标文件、当前版本和当前用户范围。越契约响应不执行，走有限协议纠偏，不能继续当正常侦察。

### P0-C：多套空转检测使用不同的“进度”定义

当前同时存在 `sceneIdle`、`recon`、`offStage`、`turns`、`noProgressSteps`、重复探针计数与截断/参数恢复预算。

其中 `lib/agent.mjs:2186–2187` 只有整轮调用全部为 `read_file/run` 时才累加 `sceneIdle`；`list_files`、`read_edit_file`、`read_scene` 反而使它归零。本次在读取中穿插列目录，即使修掉 P0-A，仍可错过“四轮后定向写场景”。

与此同时 `recon` 会继续累计，随后 `offStage` 达到阈值先暂停。不同检测器各自看起来合理，组合后却没有完成预期纠偏。

`productive` 的部分计数又在实际执行之前根据工具名更新，而最终推进在读盘后判断；“尝试写入”和“实际推进”不是同一事件。

**整改方向：**以受控工具结果和阶段产物版本变化产生统一进度事件；区分新信息、实际修改、拒绝、协议错误与失败。阶段拥有一个明确的纠偏/停止策略，不再叠加互相打断的计数器。

### P1-D：错误分类仍靠整段自然语言关键词，题材可改变恢复路径

`lib/automation.mjs:78–82` 优先把含“额度”的错误当环境故障。

隔离验证：

| 同一版式错误 | 分类 |
|---|---|
| `FAIL 版式溢出：卡片文字超出容器` | content |
| `FAIL 版式溢出：Codex 额度卡片文字超出容器` | environment |

第二条只是多了视频题材词，却会关闭内容自修。此问题尚未在本次项目下游实际发生，是复现确认的独立风险，不能冒充本次停止原因。

**整改方向：**检查器返回稳定的错误代码、类别、对象与修复位置；恢复策略读结构字段。旧输出可以适配，但不能用整个报错正文中的题材词判认证/资源故障。现有 `stage-result.mjs` 已结构化阶段身份/退出码，可在此基础上扩展，不必另造一套平行协议。

### P1-E：冲突保护能安全停住，但没有完整的受控恢复动作

分场清单绑定整份脚本和场景源的指纹。`lib/scene-drafts.mjs:44–50` 在脚本发生任何变化后拒绝继续写草稿，即使只追加注释。

`lib/scene-work.mjs:26` 对过期草稿停止分场调度；`lib/pipeline-work.mjs:121–124` 主要提示读当前场景、短补丁处理。目前没有对应的受控分场 rebase/重开事务工具。可以绕开草稿直接编辑作者场景，但不是清晰、统一、可验证的恢复流程，已写内容也难以自动判断能否复用。

本次还没写草稿，所以不是本次根因；它解释了为什么补完一处后，后续仍可能遇到新的人工处理点。

**整改方向：**保留冲突拦截，增加显式核对和重开草稿事务；按稳定场景身份、旁白版本和引擎能力核对可复用内容。不删除旧草稿、不静默覆盖，不简单忽略指纹。

## 3. 整体设计为什么反复产生这些问题

1. **流程规则存在多份来源。** `nextPipelineWork`、`pendingSceneWork`、`nextAgentStep`、`run_stage` 前置守卫和 agent 循环都维护部分状态/下一步逻辑；CLI 任务模板还在要求模型运行命令，而自动模式要求受控阶段调用。规则更新很容易只覆盖一个入口。
2. **模型同时做创作与流程控制。** 计划器已知道下一场编号和旁白，却仍给大量读取/编辑选择，再尝试靠尾注与阈值催模型动笔。程序应该管理阶段和副作用，模型负责限定范围内的创作响应。
3. **从“生成任意 JS”到正式制作，中间验证太晚。** 单场写入主要校验语法、范围和版式声明；浏览器运行、接口、版式与字幕问题更多留到后续整片检查。手写引擎代码不是原罪，但没有逐场轻量预检就把很多独立失败概率串成一条长链。
4. **恢复主要解决“不丢进度”，没有充分解决“消除原阻塞”。** 保留检查点、重置侦察次数和允许继续很有价值，但再次给同一上下文和同一动作空间，不保证模型脱离同一循环。
5. **环境不是可复现发行包。** `package.json` 没有声明/锁定运行依赖；skill 在工程外定位，新项目复制的生成器、浏览器与 Python/TTS 又形成其他版本来源。`PROJECT.json.installedFiles` 有文件指纹，但不等于完整工具链兼容契约。这是后续风险，不是本次暂停的解释。

媒体与安全模块已有实质价值：版本指纹、受控阶段退出码、原子写入、项目锁、媒体解码、字幕和抽样版式检查，不应因自动控制失败一并推翻。

## 4. 为什么测试全绿仍然不能用

本轮执行 `node scripts/test.mjs`：**1052 通过，0 失败，0 跳过**，约 32 秒。

但是新增隔离诊断仍复现了上述缺陷。两者不矛盾：

- `test/api-scene-recovery.test.mjs:123–146` 验证的是旧检查点、没有新 instruction、连续四次 `read_file`、然后模拟模型服从定向请求。没有覆盖真实入口传入首篇文章、混合读取、以及返回已收起工具的组合。
- `test/anti-crutch.e2e.test.mjs:13–14,74–83,173–178` 明确允许“完成或给出可操作暂停”；这是防止假完成的安全验收，不是无人介入成功交付验收。测试名不能代替实际断言。
- 多个媒体集成用合成替身，可以证明状态/调用逻辑，不能证明真实模型、生成 JS、浏览器、TTS 和成片的联合成功率。

因此问题不是简单“没有测试”，而是**验收目标与用户期待不一致，组合场景覆盖不足**。模拟测试仍应保留；不能改成每次单测都扣真实模型额度。另需经过授权、独立预算的真实发布验收。

## 6. 已采用的整改顺序

| 顺序 | 工作 | 必须达到的验收 |
|---|---|---|
| 1 | 冻结新功能，统一任务范围与阶段契约 | 初始文章不关闭制作授权；只读要求不被越过；模型返回任何未授权工具均无副作用；网页/CLI/恢复走同一规则 |
| 2 | 统一工具结果、进度事件与恢复策略 | 混合读取、无效工具、失败写入、相同内容重写都按真实结果分类；有限纠偏后要么推进，要么报告明确不可自动处理的原因 |
| 3 | 分场任务化，增加轻量单场预检 | 一次只处理明确场次；语法、引擎接口、代表时刻运行/版式问题在扩整片前暴露；全片组装由程序判齐后执行 |
| 4 | 明确作者稿、场景草稿和成片依赖版本 | 脚本修改后列出实际失效场次；可审计重开/迁移草稿事务；冲突不丢稿、不串版 |
| 5 | 建立可复现工具链与发布验收 | 锁定 Node/浏览器/Python/TTS/skill 能力版本；新工程、恢复、改稿均跑完整链；记录真实交付率、人工介入率、用量和失败分类 |

建议场景任务以结构化内容计划作为主路径，由已验证渲染组件处理坐标和通用运动；保留受控 JS 扩展给真正需要自定义画面的场景。不能把低质量通用模板当作“自动恢复成功”，也不应无视事实与视觉质量直接保底出片。仓库已有配方/scene-builder 等能力，须先评估内容表达和当前引擎兼容性，不能直接接入后就宣称质量问题解决。

发布门槛至少覆盖：首次长文章、选题、仅视频/发布包、横竖屏、部分稿恢复、脚本改动后恢复、用户插话、工具列表违规、失败写入、网络恢复、检查器失败、最终真实媒体。分别统计“安全停住”和“无人介入交付”；内容需要人确认与程序控制错误不得混在同一成功率里。

**不建议：**增大轮次预算、反复点击继续、自动切模型、删空转保护、放宽质检、把“暂停可恢复”改名“完成”，或只替用户手写这七场后宣布系统修好。
