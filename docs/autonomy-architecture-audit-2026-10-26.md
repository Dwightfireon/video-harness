# 独立自动运行：架构审计与优化方案

审计日期：2026-10-26。范围：指定 OpenCode session「author_edit 因 patch_text 匹配失败空转」、当前 Claude 项目的检查点/任务/日志，以及编排、编辑、检查、计划、依赖与测试代码。

本轮不修改生产逻辑、不恢复真实任务、不调用付费模型、不调整时长和质量门槛。新增文件仅为本报告和隔离诊断脚本。

## 一、结论

**是架构问题，但不需要推倒整个项目。** 确定性视频管线、项目锁、CAS 编辑、产物版本凭证已经有价值；主要缺口在于：自动制作控制面仍由一个不断叠加例外条件的 Agent 循环承担，修复事务、版本失效、错误归因与资源预算没有形成一致的协议。

所以它目前更像“遇到问题会安全停下的制作工作台”，还不是“在约定内容范围内能稳定自行完成的制作产品”。安全停下是必要能力，但不等于自动完成能力。

每次冒出“新问题”有三种不同来源：

1. 同一稿件早已存在多个问题，上一个错误挡住后续检查；修好后才看到下一层，不一定是新产生的故障。
2. 修复动作产生新的问题，或者执行器在一组修复尚未完成时抢先重跑。
3. 旧错误、旧回执与当前版本混用，让已经解决的问题继续进入修复队列。

当前证据同时支持这三类。不能把全部责任归给模型不听话，也不能把每次通过测试说成“已不需要拐杖”。

## 三、已确认的问题

### P0-1：作废旧报错的补丁，破坏了多步骤修复事务

位置：

- `lib/agent.mjs:1443–1454`：`finish_repair` 是整轮提交；要求作者输入确实变化。
- `lib/agent.mjs:1697–1699`：明确写着“一处补丁不是整轮完成，只有 finish_repair 才释放复检”。
- **`lib/agent.mjs:1781–1794`：只要文件签名变化，就直接清掉 pending。**
- `lib/agent.mjs:2106–2128`：没有 pending 后，程序立即执行下游阶段。

这几个约定互相冲突。执行器无法区分“本轮自己已打第一处补丁”和“外部用户已改稿、旧诊断失效”。修复旧错误循环时，新增的广泛失效规则又产生事务提前结束问题。

隔离复现：模拟模型分两次打补丁，生成器固定报错。得到：两次模型请求、两次窗口失效、两轮预算耗尽、**零次修复提交**。固定报错是为了观察事务边界，不是声称模拟了真实视觉修复效果。

**修法：** 每轮修复保留 `originRevision`、`workingRevision`、`repairId` 和写入来源。自己的受控写入只推进 workingRevision；外部编辑才进入冲突/重新定位流程。只在显式提交后复检。不能用“删掉所有过期检查”或“恢复时全部保留”代替来源区分。

### P1-2：错误身份混入日志路径；内容运行时错误又可能被归为环境故障

位置：`lib/automation.mjs:81–90`、`lib/agent.mjs:1430–1439`。

重复错误 key 包含整个 `reason`；reason 又包含带时间戳/UUID 的日志文件路径。同一输入、同一 `FAIL 版式溢出`，只换日志路径，就被登记为第二轮修复，不能识别为同一故障重复发生。

位置：`lib/production-failure.mjs:25–35`、`lib/production-quality.mjs:323–328`。

`检查执行失败：page.evaluate: ReferenceError: sLabel is not defined` 被归为 `environment`。但浏览器已成功运行，只是作者场景引用了不存在的变量；这是内容/场景代码错误。严格检查路径也把 renderedChecks 抛出的不同原因统一装入 checker 类。结果可能是停止内容修复、让用户去修“环境”。

**修法：** 检查器输出结构化错误，区分 `author-runtime`、`browser-launch`、`checker-internal`、`asset-load` 等来源。错误身份用稳定的 code、场号、组件 ID 和依赖范围组成，日志路径只是证据，不能参与身份。同一输入同一错误不重复扣预算。

### P1-3：机械补挂载是启发式变换，却被当成“已证明安全”

位置：`lib/scene-mount.mjs:54–74, 171–242, 245–280`、`lib/mount-repair.mjs:43–62`。

已复现：

- 合法 `root.append(a,b)` 被判定 `b` 没有挂载：扫描只读取第一个参数。
- helper 返回 `{el: Node}` 时，机械修复会生成 `root.appendChild(helperResult)`；当前 `validateSceneSource` 接受，执行时却报参数不是 Node。
- `vh.mjs:388–413` 又用这套启发式去过滤外部检查器的报错。“未检测到未挂载”被当成“确认已经挂载”，但它们并不等价。

还存在执行范围问题：`lib/agent.mjs:2078–2085` 在多个 author 阶段直接扫描并修复整项目场景，没有把 `work.path`、场号约束与正常工具的范围验证传入。真实用户要求只改某处时，自动修复路径不应另有更大的写入权限。

**修法：** 启发式先降为定位线索；自动变换只处理可证明的 Node 构造与明确授权的场次。候选须在隔离浏览器里执行并验证目标结果，再提交。未知 helper 返回值不能靠函数名猜。长期让组件 API 构造时自动挂载，减少生成端犯错机会。

### P1-4：计划、调度、质量检查不是同一份事实

实际命令：

```sh
node vh.mjs plan --dir projects/Claude是什么和Ch-1026 --json
```

返回 `ok: true`、`blockers: []`、`timing.total: 482.08`、下一步“渲染静音视频”；但实际任务因 480 秒上限停在删稿。`lib/pipeline-plan.mjs:53–56` 的 blockers 没有纳入时长限制与当前修复阻断。

另有多份时间轴判断：`lib/state.mjs:110–127` 导入项目自己的 timeline 校验，`lib/pipeline-plan.mjs:17–41` 独立解析标准数据，质量模块再做结构判断。并非没有共享代码，而是共享还不足以保证一致输出。

项目还保留了 42 条旧版式 finding 的轻量报告，但它最后采样时间为 579.71 秒，晚于当前 482.08 秒片长；报告缺输入签名，且当前 HTML 生成晚于它。**不能拿这 42 条当作当前版本的已核实问题。** 严格生产回执已有版本绑定，这是应保留并推广的设计。

**修法：** 一个只读 `observeProject` 返回当前版本、产物、阻断和回执有效性；plan、scheduler、UI 都使用它。预计会失败的硬门槛必须在计划里出现；旧报告只展示为历史证据。

### P1-5：测试更擅长验证“不误报完成”，没有严格验证“自行完成”

本轮运行现有 7 个相关测试文件：**50 项通过，0 失败**。同时，上述独立复现仍成立。

- `test/automation-agent.test.mjs:19–22` 把 patch 和 finish 放在同一次模型响应；绕开了“下一轮循环先清 pending”的时序。
- `test/anti-crutch.e2e.test.mjs:74–83, 173–178` 接受“暂停且有解释”作为通过条件。有些测试使用不能成为真实媒体的替身。它们适合检查不会谎报成功，不足以证明无人介入出片。

**修法：** 保留这些安全测试，另设自动完成测试，不允许两种目标混为一个绿色数字。必须覆盖分轮多补丁、多文件、重启恢复、旧错误消失、新问题出现、冲突、断网，以及真实浏览器和短真实媒体。每类预期明确写“必须交付”或“必须请求用户决策”。

### P2-6：运行与发行仍依赖本机环境，升级边界不完整

- `package.json` 未声明完整运行依赖，工作区无本地依赖锁文件；当前能解析 Playwright 不等于复制目录后也能复现。
- `lib/state.mjs:25–33` 默认从用户 OpenCode skill 目录找组件；`vh.mjs:382–385` 用当前全局 skill 的 checker 检查项目内复制的生成器。项目记录安装哈希是好基础，但运行期间的工具/检查器版本并非全部固定。
- `打开工作台.command:30–32` 明确要求保留终端窗口，窗口关闭服务即停止；当前入口不是持久后台服务。
- 恢复读取大量模型对话与多份 JSON 状态，无法等同于一个版本明确、可迁移的持久工作流；不代表必须马上引入大型数据库。

**修法：** 固定 runtime bundle、Node/npm/Python 与浏览器/TTS 依赖；任务记录 runtime/checker 版本，升级先做兼容检查和迁移。提供可选 launchd 后台入口与恢复监控。后台重启只恢复可证明幂等的步骤，不自动重放结果未知的付费请求或外部副作用。

这里的“依赖 OpenCode 目录/凭证来源”与“必须打开 OpenCode 才能运行”不是一回事。当前真正的问题是故障恢复仍常常需要开发者分析，而非生产链本身必须调用 OpenCode。

## 四、建议的目标架构：保留媒体管线，重做一致的控制协议

```text
网页 / CLI
    ↓ 用户要求、修改范围、时长/预算策略
任务控制器（唯一阶段决策者，可持久恢复）
    ├─ 当前项目观测 observeProject
    ├─ 纯阶段决策 decideNext(state, observation, event)
    ├─ 内容工作器：输入明确任务 → 输出候选/补丁
    ├─ 修复事务：本轮多处编辑 → 候选验证 → 统一提交
    └─ 确定性工作器：build / TTS / render / mux / verify
                    ↓
       统一发现清单 + 当前版本回执 + 事件日志
```

### 1. 模型负责有歧义的内容，不负责猜调度规则

程序决定阶段、可改对象、下一步及是否完成。模型每次拿到一个有上下文的任务：具体场次、当前脚本、组件接口、错误证据、候选基线。少量充分的信息比“再读几十轮直到找到位置”更重要。

不要仅仅拆小 `agent.mjs` 的文件：只把 2544 行拆成多个模块，原有状态冲突仍会保留。先定义状态转移，再搬代码。

### 2. 分清三个不同事实

- **有写入**：确实改变作者字节，不等于符合要求。
- **已提交候选**：这一组修改完整，可进入验证，不等于质量通过。
- **已通过**：当前候选/媒体绑定的验证结果有效。

建议基本状态：`drafting → candidate-ready → checking → repair-open → checking → producing → verifying → delivered`；另有 `waiting-user`、`blocked-environment`、`interrupted`、`cancelled`。只保留一个阶段权威，UI/task/checkpoint 中的其他字段是投影，不是独立决定下一步的状态机。

### 3. 修复预算按有效尝试计，但仍有整任务上限

保留总体最大费用、模型请求数、运行时间、无进展轮次限制；另对同一 finding 做有限修复。一个修复尝试包含多处补丁和一次提交复检。不要让一处成功补丁消耗整轮，也不要因为随便改一个文件就重获预算。

错误消失、严重程度降低或时长差距缩小应记录为收敛证据；写入备忘录、改无关文件、换日志路径不能算收敛。真实新错误也受全局预算约束，不无限续命。认证、额度、用户内容取舍必须有明确的用户入口。

### 4. 把低成本验证前置，减少后置修一整片

建议新片顺序：规划 → 脚本候选 → TTS 实测/时长收敛 → 逐场视觉生成与浏览器验证 → 全片预览/检查 → 正式渲染 → 配音混流 → 最终回执。

允许轻量模板预览并行，不必等 TTS 完才画第一张图；但不要先完成全部复杂动画，最后才发现正文需要删掉两分钟。当前目标 420 秒、上限 480 秒应实际进入写作和压缩闭环，而不只是元数据与提示。

对剩余两秒的情况，不应擅自放宽时长或加速配音；可以在已授权“自动删减冗余、不删核心事实”的范围内压缩，并保留回退版本。授权不足或改变重点时，网页应请求一次内容决策，而不是让用户找代码工具。

### 5. 中期收窄生成语言，而不是无限添加 JS 正则

对标准视频引入小型场景数据/组件层，提供自动挂载、flow/grid、安全区、稳定组件 ID 和时间锚点。编译成现有 `renderAt(t)`；保留定制 JS 的高级入口，但增加隔离执行验证。

优先迁移常见关系图、对照表、流程图，不要求重写所有历史工程。组件化不能代替浏览器检测、事实核证和人工审美判断。

## 五、实施顺序与验收条件

| 批次 | 范围 | 必须满足的验收 |
|---|---|---|
| A：先止血 | 修复事务来源/提交边界；统一当前时长 blocker；修复错误身份；约束机械修复范围 | 同一修复跨 3 次响应、改 2 个文件，只在提交后复检；预算按整轮扣；同输入同错误换日志不重复记；plan 与执行器的首个硬阻断一致 |
| B：做真正闭环 | 拆出纯调度决策；统一 findings/observations；引入候选修订与版本事件；环境错误细分 | 单元/集成覆盖每个状态转移；外部编辑不覆盖；进程中断后从明确状态恢复；作者 JS 错误与浏览器缺失走不同恢复路径 |
| C：降低缺陷率 | 脚本时长前置；标准场景组件；单场浏览器 smoke；增量局部复检 | 已授权普通内容错误能同任务自修；不靠全片反复扫描；检查器不把“未知”当“通过” |
| D：独立运行产品化 | 固定 runtime/依赖；可选后台服务；发布/回滚与任务迁移；真实完成率统计 | 另一干净环境按文档安装成功；关闭浏览器不影响后台任务；中断后不重复扣费/重放未知副作用；升级可回滚且旧项目可读取 |

A 的高置信修复先落地，不必等完整场景数据层或后台服务开发完成。每批单独验收，暂缓增加新特效、新分析器和更多自动补丁规则。

### 自动完成的验收不能再用测试数量代替

准备固定、可复现的验收集：短文、长文、超时长、复杂表格、已有成片改稿、加广告、只改发布文案、旧工程恢复。再加入真实失败行为：补丁不匹配、分轮多补丁、输出截断、场景运行时错误、检查器误报、断网、进程中止、外部编辑。

分开计量：

- 首次无人介入完成率；有界自修后完成率；等待用户内容决策率；需要开发者介入率。
- 同一错误重复次数、无效读取占比、整片重做次数、阶段耗时、模型用量/费用。
- 假完成率必须为 0；安全测试中“应暂停”的任务不能计入自动成功。

先记录基线，再约定发布门槛。例如受支持的普通案例在固定验收集中达到 90% 以上自动交付；这是建议验收目标，不是本轮已测得的完成率。网络/认证故障与需要创作取舍的案例单独统计，不能偷偷排除普通内容缺陷来美化数据。

## 六、本轮验证与边界

- 已读取指定 session 的起始事故、后续关键排查与最终结论，并核对生产现场，而不是照抄前次总结。没有声称导出并完整审阅所有历史工具消息。
- 现有测试：`automation-agent`、`automation`、`pipeline-contract`、`author-edits`、`scene-mount`、`mount-repair`、`anti-crutch.e2e`，共 50 项通过。本轮未重跑整个全量测试集。
