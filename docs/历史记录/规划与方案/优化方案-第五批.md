# 成熟度缺口分析（第五批）

分析：2026-10-18　依据：近三轮 22 个真实 bug + 现有代码盘点（38 命令 / 69 测试 / 4442 行）
原则：只列**能落成命令或测试**的缺口；每条都指向具体事故。

---

## 一、最痛的一条：**agent 不确认"你让它做什么"**

最近两轮最严重的两次翻车，都不是技术问题：

| 事故 | 表现 |
|---|---|
| 你说"简单点，给链接和优惠码" | agent 写成"价格 + 三条要点"——**绕开指令** |
| 我说"这是幻觉" | 我拿抓到的首页否定了你的指令，还改回去——**我也绕开了你** |

**共同根因：没有任何机制回读"用户到底要求了什么"，也没在收尾时核对"做到了没有"。**
`finalCheck` 只查技术一致性（时长/测量），**不查"用户的要求"**。

**可做**：
- `vh brief` —— 从用户指令里抽「必须做的（must）」与「不许做的（must not）」，存成 `out/.vh-brief.json`
- agent 启动时先打印"我理解的要求"，结束前逐条自检，**没做到就说没做到**
- 典型模式识别：`简单点/别太详细/只要 X` → 写入 must-not（不许加价格/不许展开）

## 二、**改完不给你看**（必须自己去页面点）

agent 改完只输出文字总结，**不生成静帧**。你要验证只能自己开页面、拖时间轴。
这正是"你说不对 → 我查 → 发现是 bug"循环慢的原因之一。

**可做**：`vh ask` 结束时自动跑 `vh stills`（或只截改动的场），输出图片路径，页面横幅直接给「看改动」。

## 三、**超时与中断没有语义**

- 单条命令超时 20 分钟，但**整轮没有总时长上限**
- 取消是杀进程，**没有"停下来保存到哪一步"的记录**
- 长任务（刚才 699 秒）期间你只能等

**可做**：
- 每轮写 `out/.vh-run.json` 的 `step` 字段（当前第几步、在做什么）
- 取消时写"中断于第 N 步，已完成 X"，而不是静默结束
- 页面显示"已跑 8 分钟，通常 5–10 分钟"

## 四、**内容层只有"有没有"，没有"对不对"**

`claims` 现在能查：数字有没有登记、广告有没有登记来源、每句是否可追。
**查不出**：这句描述与页面是否一致（我试了 5 轮语义比对，误报率过高，已放弃）。

诚实结论：**这一层只能人看**。所以要做的是**降低人看的成本**，而不是假装能自动判定：
- `vh claims --review`：把"每条 claims + 对应原文摘录"打成一张对照表（md），人扫一遍即可
- 广告场在 `pack` 时强制要求勾选「广告已人工核对」（已做）

## 五、工程细节（小而真）

| 缺口 | 现象 |
|---|---|
| 生成器路径与手写路径混用 | `scenes.src.js` 块数 ≠ 脚本场数时只报错，不说怎么修 |
| `vh ask` 没有 dry-run | 想先看它打算怎么做，只能真跑 |
| 错误信息有时仍是英文栈 | `spawnSync` 失败直接抛 |
| 没有"最近改了什么"的时间线 | 只能翻 `.vh-chat.log` |
