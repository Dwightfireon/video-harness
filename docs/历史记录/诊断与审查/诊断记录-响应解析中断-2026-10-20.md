# 再次中断：响应解析失败，而非重复读取暂停

## 本次现场

项目：`projects/哈囉各位聽眾大家好歡迎收-1020/`。

任务 `39d3d898-b6fd-4bf0-8f79-512b1e76285d`，第 3 次执行，本机时间 2026-10-20 17:15:13 至 17:18:40。渠道 `opencode-go`，模型 `minimax-m3.1-flash-free`。

- 本次共发出 5 次模型请求，执行 5 个工具调用，全部为只读 `run`。无写文件、构建、配音或渲染。
- 无重复读取拦截；累计检查点 51 轮，当前执行未推进计数 3，未触及 400 轮预算或停滞暂停阈值。
- 第 3 个响应明确达到输出上限，检查点只保存了推理文本，没有正文或工具调用。执行器给出拆分写入提示，并继续请求。
- 第 4 个响应正常执行一次小范围模板读取。
- 第 5 个响应收到 HTTP 200，持续接收约 77.57 秒、共 76458 字节，随后在 `parsing-response` 阶段报 `kind=response / source=protocol`，无网络错误码。当前渠道对此不自动重试，任务以 failed 退出。
- `scenes.src.js` 仍为 14:22 创建时的三场示例；脚本为十场。没有 `timing.json` 或成片。本次不是“渲染到一半失败”。

日志依据：项目 `out/.vh-chat.log:738-837`，尤其第 810、833–837 行；任务文件 `out/.vh-task.json` 及对应检查点。

## 可以确认的代码缺口

### 1. 本项目把请求输出上限固定为 6000

`lib/provider-pool.mjs:86` 对所有模型都发送 `max_tokens: 6000`。本次已有一轮明确耗尽输出预算；检查点该轮推理文本约 1.56 万字符，但没有开始写工具。字符数不能直接换算为 token 数，明确触顶的证据是响应的 length 结束及日志，而不是字符数估计。

这说明当前任务存在输出预算不足的实际问题，但不证明最后一次失败也是由它触发。简单加大上限也不能取代拆分制作。

### 2. 上次修复只补了“无工具响应被截断”的纠偏

`lib/agent.mjs` 在接收到有效响应后处理 `finish_reason=length`，提示拆分后继续。

但 `lib/provider-response.mjs:53-55` 遇到带工具的 length 响应、缺失工具信息或参数 JSON 不完整，会先抛异常，根本到不了主循环的拆分分支。`lib/provider-pool.mjs:104-107` 又统一转换为“返回格式异常”，最终停止整个执行。

**拒绝执行不完整工具是正确的安全行为；缺口是没有区分可纠偏的输出截断与真正协议损坏，而不是应该强行执行半截工具。** 上次修复未覆盖这条路径。

### 3. 诊断信息丢失，无法确定最后一条响应的具体失败类型

解析错误统一变成“返回格式异常”，未保留白名单解析子类型、finish_reason、流结束标记、工具个数等安全元数据。原始响应按隐私边界不落盘，这本身不是问题；但连无正文的安全诊断元数据也没有保存，导致无法区分：

- 工具调用被输出预算截断；
- 工具参数不是有效 JSON；
- 流未完整结束；
- SSE/JSON 结构或兼容性问题。

本轮本地模拟了“文本 length”“工具 length”“参数 JSON 缺失”“流缺失结束标记”。文本 length 能进入纠偏；另外三种情况在 requestChat 层均变成相同的 `response / protocol / parsing-response / HTTP 200`，与本次记录的分类一致。模拟说明这个诊断歧义可复现，**不能据此反推失败现场必定是哪一种**。

## 结论及下一步

本次不是此前误暂停复发；直接原因是模型返回未能通过本地响应解析。项目确有响应分类、工具截断纠偏和安全诊断不足的问题，不能把它笼统归咎于网络或渠道；也不能因 HTTP 200 就证明模型响应一定完整、格式一定正确。

优先补安全解析子类型与 finish/流结束元数据；明确截断时丢弃整批未执行工具、保留既有检查点、在有界次数内要求拆分。不能把不完整代码写进项目，也不要盲目重试所有协议错误或无限增大预算。制作层还需要可用的分场增量写入路径，不能只提示“分步写文件”却仍要求一次输出整份十场文件。

本轮只检查并新增本报告，没有修改业务代码、模型配置、用户原稿、任务记录或检查点；没有恢复任务、重启工作台或调用真实模型。既有任务仍保留可恢复现场。
