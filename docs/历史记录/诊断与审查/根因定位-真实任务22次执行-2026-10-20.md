# 真实任务反复中断：根因定位

## 结论先行

**最新中断的主因已定位到 harness 的阶段执行缺口，不是最新请求又断网，也不是视频渲染进程崩溃。**

当前流程能给模型一条“现在调用核验”的提示，却不能保证模型执行这个阶段；模型偏离后，执行器照常接受读文件、搜索、重新登记清单，12 轮后主动暂停。点击继续只重复分配同样的 12 轮，没有改变这个循环。

此外，第 12–19 次是此前改动引入的计数恢复缺陷：**没有请求模型就再次暂停**。该缺陷当前已修，但它与最新第 20–22 次的阶段不收敛不是同一个问题。上次用“629 项测试通过”概括优化结果，不能证明真实任务已经收敛，这个判断过度。

本次只调查、复现和写证据；没有修改业务代码、原稿、任务、检查点，没有启动真实模型或制作任务，没有重启服务。

## 二、最新问题的完整因果链

```text
公开作者文件中的已登记禁止词归零
  → 调度器选定 verify_change
  → 模型继续搜索方案/证据文件、扩大清单、重复登记
  → 响应不符合当前阶段，执行器仍接受并执行
  → 始终没有 verify_change 回执
  → 小步骤 12 轮预算用尽，主动暂停
  → 恢复只重置次数，重新进入相同循环
```

### 根因 A：阶段仍是建议，不是本地执行契约

位置：

- `lib/agent.mjs:1105–1125`：第三轮起设置定向 `toolChoice`。
- `lib/provider-pool.mjs:105–108`：请求体确实有生成定向 `tool_choice` 的代码路径，但仍附带全部工具。
- `lib/provider-pool.mjs:137` / `lib/provider-response.mjs:80–93`：校验结构和参数 JSON，不校验返回工具符合请求的定向约束。
- `lib/agent.mjs:1167–1170,1240`：接收返回的工具并执行，没有阶段一致性校验。
- `lib/agent.mjs:1089–1095`：第 13 次进入阶段时暂停，实际发出 12 轮请求。

**真实旁证：**第 21、22 次都只查状态、读取、搜索、登记清单，没有一次核验调用；最后进入相同停止分支。

**隔离复现：**对真实检查点及作者文件的临时副本运行当前执行器，模拟模型持续返回无关的只读工具。第 3–12 轮请求指定 `verify_change`，但这 10 次偏离仍被接受；总计执行 12 次无关读取，最后得到与现场相同的暂停文本。

另用当前 `requestChat` 的本地 fetch 替身确认：请求指定 `verify_change`，响应却返回 `list_files`，仍通过响应校验。此复现不联网，证明的是**本地缺少约束**，不是证明哪一层上游忽略了参数。

这也解释为什么增加 12 到 60 或加大总步数不是根治：只是让相同错误行为运行更久。

### 根因 B：修改范围有两种口径，核验动作又交给模型自行决定

位置：

- `lib/change-contract.mjs:6,79–84`：当前机械核验只扫描公开作者文件 `脚本.md / scenes.src.js / 发布文案.md`。
- `lib/pipeline-work.mjs:19–32`：同一集合中无命中词，就调度核验。
- 真实日志 3706–3714、3822–3830：模型反复搜索 `方案.md / claims.json`。
- 第 22 次两次调用 `define_change`（3757、3813 行），仍未调用核验。

本次现场机械扫描：

| 文件 | 已登记禁止词命中项数 |
|---|---:|
| 脚本.md | 0 |
| scenes.src.js | 0 |
| 发布文案.md | 文件不存在；不是已经审过的发布文案 |
| 方案.md | 5 |
| claims.json | 16 |

模型尚在处理内部方案/证据中的残留，程序却已认为下一步只需核验公开文件。**不能简单说模型查错了，也不能未经范围确认把内部事实依据一概删掉。正确缺口是：内部资料、公开产物和本次验收范围未形成统一、显式的契约。**

对克隆的修改合同直接调用现有 `verifyChange`，返回 `verified`；没有修改任何真实验收状态。这排除了“核验工具本身不可能通过”作为最新阻塞原因，但**不证明语义脱敏充分，更不证明成片完成**。

此外，`changesPrompt` 每轮仍重复“脱敏先 define_change”，不根据清单已存在而切换说明；`nextAgentStep`/CLI 又提供通用 build/measure/render/voice 下一步。它们不是最新暂停的直接触发器，却为重复登记和执行顺序混淆提供了条件。

### 历史根因 C：旧版小步骤计数恢复造成零请求死锁

第 12–19 次都恢复相同的 534 条消息，然后立即暂停；日志无模型请求、无工具执行。

当前 `lib/agent.mjs:881–883` 已把每次恢复的 `turns` 归零，保留历史总数。第 21、22 次确实能发完 12 轮，是真实现场旁证。因此这项已修；**不能用“这项修了”推导“最新任务不会再停”**。

### 另一个必须处理的要求遗漏

用户补充：`保留重点 和精华 至于什么小游戏 没必要放进去`。

该插话已消费且仍在对话中，但 `lib/change-contract.mjs:20–21` 的关键词匹配不认识这句，未生成独立待完成合同。本地对这句调用 `addChange` 返回 `null`。

它不是核验阶段 12 轮暂停的直接原因，但意味着即使脱敏核验通过，也不能认定用户全部要求已执行。不能只绕过 verify 就恢复出片。

## 三、为什么 629 项测试没暴露“持续完成不了”

- `test/pipeline-reliability.test.mjs:301–311` 的成功集成测试，模拟模型按预定轮数直接给出正确修改、核验和阶段调用，验证的是这些动作连接起来能否成功。
- 同文件 `204–214` 的不服从测试恰好断言“12 轮后暂停”是通过结果，只验证有限消耗，没验证偏离后的有效收敛。
- 未把“真实检查点＋真实阶段＋模型持续返回其他合法工具”作为必须处理的恢复缺陷。

所以测试全绿与真实任务反复暂停并不矛盾。**测试证明了局部正确性和停止保护，没有证明模型决策能完成真实长任务。**

## 四、请求参数与尚未证实的部分

当前所选渠道/模型：`opencode-go / minimax-m3.1-flash-free`，配置仍使用默认 `max_tokens=6000`。

临时重建的阶段请求投影约 106,917 字节，其中 system 12,673 字节、合并的首条 user 69,592 字节。它保留原材料与用户历史，不是一个干净的微任务请求；16KB 历史保留预算不代表总请求只有 16KB。**字节数不是 token 数，也没有证据说第 21–22 次因上下文超限停止。**

没有足够历史遥测来确认：

1. 第 22 次每个真实 HTTP 请求最终实际发送了什么工具约束；代码路径和实际返回不一致，不能替代线上的原始参数证据。
2. 是上游兼容层、模型实现还是其他环节没有遵守定向调用。当前日志没有逐请求的工具约束/返回工具名对照。
3. 第 3–5 次 error 的精确 API code 与上游原因，以及第 8–9 次断连发生在本机、代理还是远端。

这些未证实项不妨碍定位**当前本地循环**，但不能声称整个网络与模型链路已经彻底查清。下一次真实请求若要诊断上游，需先增加白名单遥测：执行版本指纹、请求序号、工具白名单/定向目标、实际返回工具、finish_reason、usage、耗时、网络错误码。不记录密钥、正文或长推理。不要先继续烧几十轮。

## 五、对应根因的修复验收要求（本轮尚未实施）

1. **阶段由程序完成，不靠模型自觉跳转。** 机械禁止词扫描可由执行器自动执行并记录结果；语义审阅单列，不伪造成机器可判断。扫描成功不等同整片完成。
2. **范围统一。** 显式列出哪些文件对外交付、哪些仅为证据资料，调度、提示、扫描、版本和验收只认同一范围。内部证据不因脱敏被无声篡改。
3. **本地校验阶段约束。** 阶段内只暴露必要工具；返回其他工具必须被识别并产生有限纠偏/可执行阻塞，而非照常执行直到 12 轮暂停。上游即使忽略 tool_choice，本地也应正确。
4. **所有插话有处置结果。** 不能以几个关键词决定是否纳入要求；“不放小游戏”需要修改计划、脚本和画面的独立验收路径。
5. **用当前检查点作回归输入。** 验证无法无限重新登记、无法反复搜内部文件耗尽预算，核验后真正转入正确阶段；也验证新增小游戏要求没有丢失。成功标准不是“这次没假报完成”，而是“完成了可完成的小步骤，或给出准确、不会原样复发的阻塞”。
6. **再做受控真实验收。** 当前本地复现不能代替真实渠道能力验证；若要用付费渠道，不自动发请求，先限定请求次数与诊断范围。
