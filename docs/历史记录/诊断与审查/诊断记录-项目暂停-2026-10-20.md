# 项目再次暂停：现场诊断

调查日期：2026-10-20。以下时间均为本机时间（UTC+8）。

项目：`projects/哈囉各位聽眾大家好歡迎收-1020/`

任务 ID：`f2c43f2b-36e4-44dc-b5d1-e9a4006082f8`

## 结论

这不是一个原因重复发生，而是两个不同的停止原因：

1. **第一次：400 个模型请求轮次耗尽，正常保存检查点后暂停。** 大量步骤消耗在重复查看目录、模板、源码和配方上；第 367 轮才首次通过 `write_file` 写方案。仅提高预算不能解决这种空转。
2. **第二次：TLS 证书域名不匹配。** 10:58:39 的请求在等待响应头阶段报 `ERR_TLS_CERT_ALTNAME_INVALID`，45ms，收到响应正文 0 字节。没有达到第二轮的 400 步预算。

没有证据显示这两次停止是额度不足、内容审核拒绝、192 KiB 本地硬拦截或此前工作台重启所致。日志中确有一次 `ECONNRESET`，但同渠道重试后继续执行，不能把它认作第一次暂停原因。

## 1. 第一次为什么做了 400 步还没完成

从完整检查点按 assistant 工具轮次重建顺序，而不是使用网页日志尾部的步数显示：

| 事项 | 现场事实 |
|---|---|
| 模型工具轮次 | 400 轮 |
| 工具调用 | 411 次；一轮可包含多个工具 |
| 工具分布 | `run` 387 次、`read_file` 21 次、`write_file` 3 次 |
| 模板检索 | 163 次 `run` 提及 `engine.tpl.html` |
| 首次通过写文件工具写方案 | 第 367 轮：`方案.md` |
| 写脚本、证据台账 | 第 372 轮：`脚本.md`；第 374 轮：`claims.json` |
| 工具拒绝 | 30 次（不等于 30 次付费请求失败） |
| 暂停时视频 | 尚无成片 |

### 明确卡住的制作关口

第 375 轮尝试构建，工具结果包含：

```text
✗ scenes.src.js 有 3 块，脚本有 10 场 —— 对不上（一块一场）。
✗ 生成 scene.html（估算节奏）失败
```

但这条复合命令使用管道并继续执行 `clarity`，最终工具返回的第一行是 `exit=0`。因此“外层命令成功退出”不等于构建成功。

调查时 `scenes.src.js` 和 `scene.html` 的修改时间仍是项目创建时，`timing.json`、`out/video-voice.mp4` 不存在。模型没有把新写的 10 场脚本落实为对应场景，更没有进入正式配音与渲染。`PROGRESS.md` 也仍全部标为“未开始”。

第二次恢复后的 50 个成功工具轮次全部为 `run`，没有 `write_file`。随后第 51 个请求遇到证书错误。不能把“检查点恢复成功”当作“创作已恢复有效推进”。

### 已复验：状态投影丢了近期产出回执

使用当前 `prepareRequestContext()` 对真实前 400 轮历史重新计算，结果可稳定重现：

- 完整历史为 813 条消息，请求投影为 18 条消息（system、原始要求及最近 8 轮工具调用/结果）。
- 台账达到上限，标有“台账过长已截断”。
- 完整历史中存在 `write_file(方案.md)`、`write_file(脚本.md)`、`write_file(claims.json)`；但三个写入回执均不在台账中，也不在保留的最近工具调用中。

原因是 `lib/request-context.mjs:43-82` 按签名首次出现的顺序组织台账，超长后直接截取前 24000 字符。大量早期探索占据了前缀，后期实际产出反而被截掉。“当时的判断”放在动作列表之后，也可能一起被截掉。

`worklogBlock()` 只在新建对话时加入 system；恢复沿用 `saved.messages`，没有重新加入当前台账，每个请求前也不刷新。同时磁盘工作台账混存读取和写入，只保留最近 60 条，当前生成的摘要已经没有“已写文件”栏目。两套机制没有可靠地互相补偿。

这证明的是**近期产出回执从发送投影中丢失**，不是原始要求或磁盘检查点丢失。近期其他读取仍可能包含文件正文；不能把它夸大成模型完全看不到这些文件，更不能证明所有重复操作都由这一处造成。大量探索在台账到顶前就已发生。

### 已能直接定位的执行器缺陷

- `lib/agent.mjs:168` 的正则只要看到 `gen.mjs`、`render.mjs`、`voice-kokoro.py` 就拒绝，并没有区分“执行”和“只读查看”。真实记录中的 `sed -n 1,120p gen.mjs`、`grep ... voice-kokoro.py` 因此被误拦。
- `lib/agent.mjs:175` 只防连续完全相同的命令，主循环也只比较连续调用；隔几步再读、换一个范围或用 Python 读取，均不会被当作循环。
- `read_file` 的短期去重不能覆盖主要由 `run` 发起的 `cat`、`sed`、`grep` 和 Python 读取。本次第一次执行有 387 次 `run`，仅 21 次 `read_file`。
- 缓存命中也未核实“内容是否真的完整可见”：第 284、340 轮读取的 `gen.mjs` 原结果有 7180 字符，请求投影只保留头尾；第 287、343 轮重读却被提示“内容就在上面几步里，不必再看”。这会阻止补读刚被节选掉的中间部分。
- `run` 仅保留输出尾部 6000 字符，随后请求投影还会进一步节选。对查源码而言，工具“成功”不代表模型收到了它需要的完整片段。
- `lib/server.mjs:490` 将退出码 0 直接记为 `══ 完成 ══`，而预算暂停的 CLI 也退出 0。真实日志因此紧接“达到 400 步暂停”又显示“完成”，两者相互矛盾；任务状态本身仍可保留为暂停。

这些是可从代码和历史调用验证的缺陷。它们解释了现有保护为什么没挡住空转；不能据此证明模型每一次重复读取的内部原因。

## 2. 第二次为什么又停

时间线：

| 本机时间 | 事件 |
|---|---|
| 09:51:59 | 初次任务开始 |
| 10:55:15 | 第二次执行恢复，读取原任务 813 条消息 |
| 10:55:22–25 | 本机 Clash Verge 启动内核并设置 DNS |
| 10:58:39 | OpenDesign 请求遇到 `ERR_TLS_CERT_ALTNAME_INVALID`，第二次执行失败退出 |
| 10:59:02 起 | 无凭证 TLS 检查已可取得合法证书 |
| 11:01:50 检查时 | 现场已进入第三次执行；不是本轮调查触发的继续 |

错误来自证书主机名校验，不是模型返回的额度、认证或内容审核结果。执行器不重试证书错误、不切渠道、不忽略证书校验，这部分行为符合安全边界。

### 网络路径实测

- 请求主机：`amr-link.open-design.ai`。
- 本机 DNS 当时返回 `198.18.0.19`，路由经 `utun4`，网关 `198.18.0.1`。
- 本机存在运行中的 Clash Verge / mihomo。因此即使系统 HTTP 代理和 `HTTPS_PROXY` 未启用，也不能认为此请求绕过了代理；TUN 仍接管该路径。
- 首次诊断握手成功；随后连续 12 次独立 TLS 握手均成功，证书覆盖 `*.open-design.ai` 与 `open-design.ai`，证书有效期为 2026-08-25 至 2026-11-23。
- 随后 5 次不带认证的 `HEAD /` 请求均取得 HTTP 404。根路径 404 不等于 TLS 故障，也不证明模型生成接口正常。

**证据边界：**历史诊断保存了安全错误码，没有保存当时错误证书的域名、指纹及实际远端地址。因此已证明“当时发生证书域名不匹配”，但尚不能证明是 TUN/DNS 映射、某个代理出口，还是服务端证书路由造成。后续检查正常也不能抹掉这次历史故障。

## 3. 建议的处理顺序

1. **先治空转，不再仅把 400 改成更大数字。** 对“长期没有作者文件变化、反复检查相同材料、构建持续失败”识别停滞；先给明确的下一关纠偏，仍无进展再以具体原因暂停。不要自动无限续跑付费模型。
2. **让恢复能看到有效现场。** 持续维护当前制作阶段、最新成功和失败的关口、文件状态与下一步；不要只依赖很短的工具窗口及命令回执。
3. **修复工具误拦与结果语义。** 区分只读检查与绕过管线直接执行；为读取提供范围；把构建失败保留为失败，不让后续 `clarity` 或管道的退出码覆盖它。
4. **修复状态呈现。** 预算暂停不得再附加“完成”；证书错误直接解释为“证书域名不匹配”，而不只是笼统的“网络连接失败”。
5. **网络故障补最小安全证据。** 下次记录预期主机、错误证书的公开域名/指纹及连接路径信息，仍不保存密钥、正文或请求头。不关闭 TLS 校验，不自动改渠道或代理配置。
