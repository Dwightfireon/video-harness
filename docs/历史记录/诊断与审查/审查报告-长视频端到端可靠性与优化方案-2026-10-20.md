# 长视频端到端可靠性审查与优化方案

审查时间：2026-10-20 20:14 起。对象：当前 harness 代码及用户项目 `projects/哈囉各位聽眾大家好歡迎收-1020/`。

本轮是 review：不修代码、不恢复任务、不改原稿或检查点，不调用真实模型。仅新增本报告；验证使用读取现场、ffprobe、现有测试及独立临时目录中的本地模拟。

## 一、结论先说

**目前尚不能把本项目视为可靠的“一键长视频生产流程”。不是单一网络问题，也不是用户的指令写错。**

当前系统的核心仍是“一个模型在通用工具循环里自行推进全部工作”。已有检查点和保护机制能减少损坏、阻止执行半截工具，但没有把“当前该修哪个文件、哪一场、怎样算通过、哪些下游必须作废”变成可靠的执行计划。

前几轮修复有价值：分场落盘确实写出了十场；画幅已明确保存；截断不会写坏文件；任务完成/暂停的展示比之前准确。但是，**这些修复更多解决了安全停止和进度保留，没有打通修改、脱敏、重建和发布验收的完整闭环。此前不能以局部测试通过代替长视频流程已经稳定。**

最该做的不是继续增大 400 步预算，也不是无限调高输出额度，而是：

1. 先统一产物新旧判断和真正的交付标准。
2. 给已有稿件、已有场景提供小块修改与按场验收路径。
3. 由程序按阶段调度，把模型约束在当前小任务里。
4. 在这套结构内做有界网络恢复、模型预算配置及故障注入验收。

## 三、重要发现（按优先级）

### F1｜P0：分场机制没有覆盖“已有成片的修改与脱敏”

**位置：** `lib/scene-work.mjs:13–29`、`lib/agent.mjs:739–752, 920–949`、`lib/scene-drafts.mjs:39–45, 79–97`。

`pendingSceneWork` 遇到草稿 stale、场景已齐、没有缺场等情况会返回 null；定向写入又依赖这个结果。用户新补充/插话会禁用定向写入，以免覆盖用户要求，这个保护本身合理，但没有另一条“按新指令修当前一场”的调度路径。

当前十场草稿都在，但 `sceneDraftStatus.stale=true`，`pendingSceneWork=null`。脚本在分场组装之后发生过修正，草稿清单的全局脚本哈希和现稿不再一致。**保护旧稿不被覆盖是正确的，缺的是安全进入下一轮编辑的机制。**

因此，此时提示“用 write_scene 分场写”并不等于已有可用的小块编辑流程。`write_file` 仍要求整文件内容，`scenes.src.js` 已有约 37 KB/827 行；没有正式的 `read_scene / replace_scene / exact text patch` 工具。模型又考虑重写整份，截断后仍只收到同类提示。

**影响：** 初次生成能落盘，修稿和临时要求却回到大任务循环。单纯继续运行很容易再次触顶或空转。

**建议：** 按当前作者文件创建新的编辑版本；提供按场读取/替换、带 baseHash 的精确文本补丁。不要删掉冲突检查，而要用版本化、显式基线和原子提交解决冲突。

### F2｜P0：状态系统互相矛盾，可能把旧视频当成可复用视频

**位置：** `lib/state.mjs:237–267`、`vh.mjs:453–467, 192–203, 714–743`、`lib/deliverable.mjs:25–32`。

`measure` 即使只是为未变的脚本重跑，也会重新生成文件并清空 render/voice 基线。随后 snapshot 先发现缺基线，却又在“媒体时长与时间轴相同、没有 render 基线”时删除 `stale.render`。**时长相同不能证明画面版本相同。**

当前只读实测：

```text
snapshot.stale：只有 voice、stills，没有 render
CLI 的下一步建议：vh voice --srt
deliverableState：成片早于 engine.tpl.html，需要重新测量与渲染
```

独立临时目录也复现了同样矛盾：更新模板后视频时长不变，snapshot 不要求重渲，deliverableState 却判过期。

**影响：** `go` 和模型可能被导向“给旧视频加旁白”，末尾检查又要求重做；用户看到的是反复绕路。此处的“需要重新测量”还过于笼统：仅画面/模板改变时，不一定需要重新合成测量旁白。

**建议：** 共用一个产物依赖判断：输入内容哈希、引擎哈希、时间轴、尺寸、音色/语速、需求版本共同决定是否复用。缺基线不能因时长相同而升级为有效。measure 不变则不清空有效渲染基线。

### F3｜P0：全流程完成标准仍会接受“无旁白、没执行新要求”的视频

**位置：** `lib/deliverable.mjs:10–17, 46–57`；`lib/agent.mjs:1025–1053`；`lib/brief.mjs:138–161`。

完成判断从静音和有声视频中选较新的一个，并没有要求全流程最终产物必须有旁白。也没有把用户新指令转换成可验收的需求版本。brief 自检主要覆盖链接、优惠码、价格等特例，不覆盖本次的人名脱敏。

**独立本地复现：** 创建只有画面的 1 秒测试 MP4；脚本保留“张三”；任务要求把“张三”替换为“受访者”并交付带旁白视频；模拟模型只回复“已完成”。结果：

```json
{"status":"completed","nameStillPresent":true,"voicedMp4Exists":false}
```

这不是说当前用户任务已经误标 completed（当前没有），而是证明完成判断仍存在这个可触发缺口。

**建议：** article/topic 必须核验当前版本的最终 MP4、真实音频流、字幕、时长、尺寸及需求执行记录。用户明确不需要旁白时才允许相应例外。脱敏至少检查已识别实名是否仍出现在公开脚本、画面文案、字幕和发布文案中；语义审阅不能被简单词表完全替代。

### F4｜P1：临时断线恢复只覆盖 OpenDesign，当前渠道仍一断即退

**位置：** `lib/network-diagnostics.mjs:77–83`；`lib/provider-pool.mjs:191–229`。

`canRetryRequest` 第一项就排除非 opendesign。第 8、9 次的 opencode-go ECONNRESET 因此直接结束执行，而不是进行一次有界恢复。此前修复没有覆盖到用户实际使用渠道的这类故障。

**建议：** 根据故障类型和渠道能力决定有限重试，而不是只按渠道名称。对可识别的临时连接问题设请求/阶段/任务级预算、退避和取消响应；额度、认证、内容拒绝、证书及不明故障不盲重试，不换渠道。重试模型请求不能重放已执行工具；还应承认请求可能已在服务端计费，控制重复费用风险。

### F5｜P1：Shell 管道能把真实失败变成 exit=0

**位置：** `lib/agent.mjs:274–288`；`lib/tool-result.mjs:2–12`。

工具使用 zsh 执行复合命令，没有开启 pipefail。模型频繁使用 `vh ... 2>&1 | tail/head`；退出码可能只表示 tail/head 成功。文本摘要也不可能还原已被截掉的错误。

**本地复现：**

```text
执行：node -e "process.exit(7)" 2>&1 | tail -3
工具回执：exit=0
toolOutcome：ok=true
```

**建议：** 核心制作改为结构化 `run_stage`，程序以 argv 启动命令并直接捕获真实退出码、全量日志和产物验证。短期加 pipefail，避免 agent 用 tail/head 控制执行本身；展示层可以裁日志，执行层不能丢失败。

### F6｜P1：写权限与画幅限制可以被通用 run 绕过

**位置：** `lib/agent.mjs:128–142, 211–216, 243–276`；`lib/video-format.mjs:95–107`。

write_file 的模式和画幅检查并不约束 run 中的 Python/Node/Shell 写入。命令名前缀白名单不是文件系统沙箱。

**临时目录复现：** edit-copy 模式直接 write_file 修改脚本被拒；同一模式用 Python 经 run 写脚本，返回 exit=0，文件实际变更。没有改用户真实文件。

现场还曾出现 `python3 -m pip install --user zhconv`，说明模型可以把修改项目扩展到用户级环境。不能把这种能力误描述为“严格按模式限制写入”。

**建议：** 把主要写入收口到受控工具；核心 stage 只允许固定命令和参数。安装环境依赖应是用户确认的预检流程，不应由制作循环临时全局安装。若保留任意 run，要明确它不是强安全边界，并另做隔离，不能只继续加正则。

### F7｜P1：恢复只是续上大对话，不是恢复一个确定的小步骤

**位置：** `lib/agent.mjs:716–752, 917–958, 1007–1016, 1055–1095`；`lib/request-context.mjs:119–134, 197–228`。

- 较早历史虽已压缩，最新 assistant 推理仍保留；已有错误判断、旧方向和重复规划仍会回到输入中。
- 输入按字节而非模型实际 token/窗口预算控制；本次发送约 138–158 KB，不能直接把这些字节等同于 token 或据此证明上下文超限。
- 截断后仍用同一个大任务、相同输出额度重问；只增加“请拆小”的提示，没有强制转成可执行的补丁。
- 截断计数保留，但只读工具可重置它；其他未推进计数只在工具分支更新，纯文字/触顶分支不等同计入阶段推进。
- 本次 `noProgressSteps=0` 不代表脱敏已推进：最后一次 measure 更新了中间产物，随后触顶并不经过工具后的推进统计。

**建议：** 保存 stage/subtask、阻塞原因、输入哈希及已提交输出。恢复时从文件与当前需求生成小而新的工作包；完整历史留档，不必将全部旧计划继续作为工作上下文。达到截断上限后，重试必须有具体策略变化，否则不提供“照旧再跑”的假希望。

### F8｜P1：测试覆盖了局部保护，却缺少真实用户路径的交付验收

**位置：** `test/truncation-scenes.test.mjs:144–164`、`test/av-sync.test.mjs`、`test/film-integration.test.mjs:28–40` 等。

本轮全量复测：**473 项，472 通过，1 失败**。失败仍是 film-integration 依赖不存在的 `projects/comet/gen.mjs`，未跳过。

现有测试证明不少局部能力是有效的，但不能证明真实模型会完成长片。比如“截断→分场→完成”测试使用预先安排的模拟响应，且以 edit-visual 模式完成草稿；并未验证“已有十场 + 更换画幅 + 插话脱敏 + 草稿基线变化 + 修布局 + 全流程有声交付”。

本轮复现的静音误完成、状态矛盾和管道吞错没有被现有绿灯阻止。**测试数量不是验收标准。**

**建议：** 修掉依赖用户演示项目的测试 fixture；加入真实文件操作/本地模型网关/本地媒体生成的长链路和故障注入。真实模型长片试跑必须另行获得费用授权，并以最终产物验收，不只检查退出码。

## 四、优化方案：先救当前片，再修产品闭环

### A. 当前项目的最小救援路径（不是再从头生成）

本轮不执行，下列是建议实施顺序：

1. **冻结当前现场。** 保留原始 materials、现稿、十场代码、测量缓存及旧视频，作为明确的基线版本。
2. **把新要求列为待完成修改。** 固定 16:9；为“移除政治相关表述、人物匿名化”建立变更清单。不要篡改私有原始材料来伪装已脱敏；公开脚本、画面、字幕与发布文案才是审阅重点。
3. **先做稿件精确补丁。** 按段替换姓名和需调整的表述；同步 claims 的公开文案与来源关系。每次验证替换范围，避免一口气重写方案、claims、全脚本和全场景。
4. **再按场修画面。** 从当前 scenes.src.js 取基线，每次只修改一场；先解决已知越界、重叠与脱敏文案，过语法和实际采样检查后提交。不要继续沿用已 stale 的整片草稿清单强行覆盖。
5. **按依赖决定重测。** 文案变更使受影响的 TTS 测量缓存失效，未变句继续复用。仅布局变化不要求重做整份 TTS。修完当前稿后再确定最终时间轴。
6. **确定性收尾。** build → 必要的 measure → 需要的整片 render → voice/SRT → 交付验证。此阶段不让模型再去探索模板或临时改业务目标。
7. **发布验收。** 真实 1920×1080、有旁白音轨、字幕与时长一致；匿名化检查通过；不是旧视频或旧旁白。与项目当前需求版本绑定后才记 completed。

### B. 产品优化的实施批次

| 批次 | 工作 | 主要落点 | 交付标准 |
|---|---|---|---|
| P0-1 先修真实性 | 统一状态、不可用时长证明新旧、严格有声/需求验收、真实命令退出码 | state、deliverable、CLI、工具执行 | 同一现场的 UI/status/go/final 给同一结论；静音或未执行需求不能完成；管道失败不能成功 |
| P0-2 再修可修改性 | 按场读取/替换、精确文本补丁、编辑版本/CAS、需求修改清单 | scene-drafts、新增编辑工具、checkpoint | 现有十场可安全改其中一场；脚本改变后有可恢复编辑路径，不盲覆盖也不被锁死 |
| P0-3 修调度 | 持久化阶段、小任务队列、每任务读/写/输出预算、截断后降级为补丁 | agent、新增轻量 pipeline state | 一次操作一个明确文件/场景；失败只回到当前小步，恢复不重做已验收部分 |
| P1-1 修恢复与预算 | 统一可恢复网络分类、阶段级有限重试、按模型配置额度/推理能力 | provider、network diagnostics | 注入临时断线可有界恢复；永久错误停止；不换渠道、不重放副作用、不无限付费 |
| P1-2 修体验与测试 | 当前阶段/待完成要求可见、长命令进度、质量检查结构化、端到端故障测试 | server/UI、check adapters、test | 用户能区分“已排队/已接收/已应用/已验收”；测试证明最终媒体而非仅提示流转 |

不需要一次性推翻已有渲染器或 TTS。优先保留可用的缓存、增量渲染与检查点，把“谁决定下一步”和“如何验收”收回程序。

### C. 建议的轻量状态模型

```text
任务：taskId + attemptId + requirementsRevision
阶段：script_edit → claims_sync → scene_edit(Sn) → build
      → measure_if_dirty → render → voice/subtitles → validate
每阶段：inputHashes / outputHashes / status / retryBudget / blocker
插话：queued → received → applied(具体文件/场景) → verified
```

插话到达后先更新需求版本。尚未执行的旧版本副作用要在安全边界核对，不能只把指令放进对话就继续执行旧计划。已经完成的副作用不假装撤销，明确标记哪些产物需要重做。

阶段上下文应包括：当前要求、该阶段必要原文、相关文件/场景、最近一个失败、允许的动作、通过标准。不要再把几十轮旧接口探索当作主要记忆。

## 五、验收标准：以后怎样证明真的修好

### 必须补的自动化回归

1. 无音轨或没有最终混流文件，全流程不能 completed；用户明确无旁白任务除外。
2. 同时长视频在脚本、引擎、尺寸或需求版本变化后必须判旧；status/go/final 结论一致。
3. `node -e "process.exit(7)" | tail` 必须是工具失败，不得登记成功。
4. 已有十场后修改脚本/脱敏，能安全创建编辑版本、逐场替换并继续组装，用户额外修改触发 CAS 冲突而非被覆盖。
5. 模型先耗尽推理预算、连续输出 length 时，程序切为一个明确的小补丁；仍失败则给具体阻塞信息，而不是只建议继续。
6. opencode-go 注入 ECONNRESET、延迟头、流中断：按策略有限恢复，不重复执行已完成写入。额度/认证/策略拒绝不盲重试。
7. 插话在请求中、工具批次中、恢复前后到达，均不丢、不重复应用；已接收但未完成必须在界面显示待完成。
8. 取消/进程被杀后，未知副作用先核对；编辑模式不能经通用 run 越界写或取消画幅约束。
9. 十场场景＋脚本变更＋画幅选择＋插话修改＋字幕＋音轨的完整本地链路通过；最终按媒体真实内容与需求版本验收。
10. 简繁体元数据兼容、误报内部术语等检查器问题应有独立回归；机器硬约束和审美建议分级，不用绕过检查或篡改含义解决误报。

### 真实模型验收

本地模拟通过后，经用户授权，使用当前渠道先做短片，再做一条接近当前规模的长片。记录请求次数、阶段耗时、缓存命中、重试次数与最终输出。

“一次性生成”应定义为：用户提交后无需反复人工点击继续，程序内部允许有限重试和检查点恢复；遇到认证/额度等不可恢复问题明确停止。不能承诺网络永不中断，也不能通过无限重试来凑成功。
