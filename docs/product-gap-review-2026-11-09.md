# 映序：产品成熟度与代码缺口复核

日期：2026-11-09。范围：当前工作副本，分析与验证，不实施产品改动。

## 一、结论

**映序已经有扎实的视频制作底座，但仍是需要熟练操作者兜底的本地工作台，尚不是普通创作者可以稳定依赖的成熟产品。**

主要差距不是页面数量、动画数量或模型数量，而是：

1. 用户设置、任务要求和真实执行没有贯通。
2. 执行结束、交付有效、用户认可、平台收稿几个状态仍会混用。
3. 新的 OpenCode 路径没有完整继承旧执行器的恢复、受限修改和自动化契约。
4. 预览代码、工作台控制接口、发布凭证处在过于接近的信任域。
5. 队列与发布的跨进程事务、崩溃恢复没有形成闭环。
6. 安装、升级、质量回归和故障支持仍依赖开发者本人。

建议先确定一个可兑现的产品范围：**macOS、单人、本机运行的文章/选题讲解视频工作台；先可靠完成一支，再支持可靠地连续制作多支；发布始终另行授权。** 不应先扩成云平台、团队协作系统或全平台自动运营工具。

## 二、复核方法与边界

- 交叉阅读 CLI、网页、OpenCode/local 两种执行器、任务/进程管理、队列、发布、资源预算、安装入口及说明文档。
- 使用临时目录、假 OpenCode 可执行文件、假发布服务和 Playwright 复核关键链路；不调用付费模型、不登录、不上传或提交真实稿件。
- 定向测试：7 个文件，**79/79 通过**。这不是全仓测试结果。
- 临时复核目录已清理；未修改现有视频、工程、凭证、守护进程或工作流配置。本文是本轮新增的分析文档，不是修复完成回执。
- 下文区分“隔离复现”“静态确认”“待专项验证”。安全复现使用虚拟文件与假服务，不代表发生过实际泄露或真实投稿。

本轮测试命令：

```sh
node scripts/test.mjs test/runner-batch-schedule.test.mjs test/schedule.test.mjs test/publish-guard.test.mjs test/publish-api.test.mjs test/task-resume.test.mjs test/production-lock.test.mjs test/production-cli-lock.test.mjs
```

## 三、已有能力应该保留，而不是推倒重来

| 已有基础 | 价值与边界 |
|---|---|
| 作者文件、生成物、阶段指纹与增量计划分离 | 已经能回答哪些阶段失效，避免无意义整片重做；不等于全部动态依赖都覆盖 |
| 配音实测、字幕、媒体有效性及版本检查 | 不是只判断 MP4 是否存在；技术有效不等于讲述和视听质量好 |
| 跨进程生产锁、任务 attempt 身份、取消与子进程登记 | 已有实质性可靠性投入，相关故障测试通过；OpenCode 共享服务中的工具生命周期仍需专项核验 |
| 本机绑定、写来源检查、私有状态下载限制、回收站保护 | 不是毫无安全防护；但保护范围仍有缺口，见下文 |
| 发布用例层与网页/Electron 适配层分开 | 可复用的结构已经存在，但发布防护尚未全部下沉到共同入口 |
| 内容优先政策 | 不应为产品化重新增加默认付费审稿、两版试稿、人工签字或额外阻塞 |
| 映序界面与统一视觉语言 | 已能承载完整流程；下一步重点是让展示与真实执行一致 |

相关代码：`lib/artifact-status.mjs`、`lib/pipeline-plan.mjs`、`lib/production-lock.mjs`、`lib/process-lifecycle.mjs`、`lib/author-edits.mjs`、`lib/workflow-policy.mjs`、`desk/service.mjs`。

## 四、按用户旅程看差距

| 用户旅程 | 当前主要断点 | 成熟产品应做到 |
|---|---|---|
| 第一次打开 | 需要人工准备 Node、OpenCode、Chrome、Python/TTS、外部 skill；网页就绪判断偏旧路径 | 开始前知道缺什么，按实际执行器检查；有不付费的安装自检和明确修复入口 |
| 配模型、开始制作 | 设置页选择与 OpenCode 调用来源不同 | 用户可核对实际 runner、provider、model、endpoint 来源；配置错误明确阻断，不静默换渠道 |
| 输入文章或选题 | 缺少轻量、可检查的结构化制作要求；长原文又被传入子进程参数 | 原文可靠留存，受众、范围、画幅、交付目标等要求随任务保存，默认不强加问卷 |
| 等待制作 | 日志阶段来自命令正则；流程结束可能先于有效交付 | 分开显示执行状态与交付状态，未知即未知；下一步具体且不会误触付费任务 |
| 中断后继续、补一句要求 | OpenCode 接续会话不等于继承本产品的新增要求与恢复约束 | 新要求确实送达，旧 attempt 不能覆盖；恢复方式、能力和限制如实显示 |
| 只改画面/只改文案 | local 有程序约束，OpenCode 主要依靠提示词 | 不允许修改的文件和阶段有统一约束；越界可检测、停止并保留用户改动 |
| 连续生产 | 队列原子写文件不等于派发事务；空队列补题路径有逻辑断点 | 不重复建片、不丢队列更新；崩溃后知道“未派发/已派发/需核对” |
| 看成片、改一处 | 已有预览、分镜与修改入口，但缺统一版本历史和视听问题闭环 | 用户知道改了什么、影响哪些阶段，能按版本对比并安全恢复 |
| 发布 | 预检、提交、日志和批量流程的保护分散 | 单条、批量、Electron 共用同一不可逆动作事务；未知结果先核对，不靠等待推定未提交 |
| 用一个月以后 | 安装、日志、缓存、升级与故障支持较工程化 | 可诊断、可迁移、可升级回滚，支持包脱敏，缓存与原始材料清楚分开 |

## 五、已定位的高优先级问题

这里 P0 表示“面向普通用户推广前必须解决的安全或核心信任问题”，不是断言当前已经发生事故。P1 是持续使用前应补齐的可靠性问题。

### G01 · P0：预览 HTML 与控制台同源，能够访问控制接口

**证据：隔离浏览器复现。**

- `www/player.html` 的预览 iframe 未设 sandbox；`www/panel.js:196–203` 直接加载同端口项目 `scene.html`，并通过 `contentWindow` 调用画面运行时。
- 在临时工程放入测试 `scene.html`，打开真实项目页。测试脚本能够修改父页面，并向 `/_api/publish/submit` 发送 `confirmed: true`。
- 只有状态响应和提交服务替换为 fixture；假发布服务确实收到请求，未发生真实投稿。

**影响：** 生成或导入的 HTML 一旦包含不应有的脚本，就具有工作台同源脚本的权限。用户在界面点击确认的意图，不能仅靠一个客户端布尔值保护。来源校验挡不住本来就同源的预览。

**方向：** 将画面运行域与工作台控制域分离；以受约束的消息协议控制 `renderAt` 等操作，并限制画面对控制接口的访问。不能只机械添加同时允许脚本和同源的 sandbox，也不能只给危险按钮加确认弹窗。

### G02 · P0：静态文件范围过宽，路径字符串检查未覆盖符号链接

**证据：隔离 HTTP 复现。**

- `lib/server.mjs:992–1027` 以仓库根为静态根，只特判 `vh.config.json` 与 `.vh-*` 路径，随后 `statSync` / `createReadStream`。
- 临时根目录的 `/.env` 返回 200；指向临时根外虚拟文件的符号链接也返回 200 并能读取内容。
- 自定义外部 Host 的 GET 请求仍返回 200；写来源校验仅应用于写请求。其他本机端口来源的写请求也会通过 `writeOriginError()`。

**影响：** 非公开文件和符号链接目标可能进入 HTTP 可读范围。Host 行为构成 DNS rebinding 防线缺口，但本轮没有搭建完整外网攻击链，不能声称已复现远程攻击。

**方向：** 静态资源采用明确的公开范围；真实路径和打开文件时均处理链接边界；所有请求验证允许的 Host，浏览器写入验证精确 Origin。单纯隐藏文件名、仅绑定 loopback 或加入 CORS 不是完整修复。

### G03 · P0：执行器正常退出被直接记为完成，未结合任务目标核验

**证据：真实 CLI + 假 OpenCode 复现。**

- `lib/runners/opencode.mjs:270–280`：无错误事件、退出码为 0，即返回 `completed`。
- `vh.mjs:2626–2636` 将结果直接传给 `finishTask()`。
- 假执行器只输出一句普通文本，不写脚本或视频。任务最终仍为 `completed`，同时 `taskStatus()` 报告“成片还没生成”。
- `lib/schedule.mjs:127` 又将 `status === completed` 直接推导为 `done`。

**影响：** 同一工程在不同页面/模块里可能同时“完成”和“没有交付物”。既有旧片时，也不能仅以旧片有效证明这轮修改已落实。

**方向：** 分离 `execution`、`delivery` 和用户验收状态；由统一、目标相关的完成契约收尾。只改文案不能要求重出 MP4；新建视频不能只靠进程结束；明确不需要改动的请求也不应机械判失败。使用已有产物凭证，不另造一套重复质检系统。

### G04 · P0：OpenCode 续跑漏传已保存的补充要求

**证据：真实 CLI + 假 OpenCode 参数捕获复现。**

- `resumeTask()` 保存了“继续时只修第二场，绝不改原文”。
- `vh.mjs:2623–2629` 向 runner 传入 `instruction` / `instructions`，但 `lib/runners/opencode.mjs:173` 未接收这些字段。
- 实际子进程 prompt 包含原始任务，不包含上述新增要求。

**影响：** 页面显示已提交、任务文件也保存了要求，不代表模型收到。接回旧 OpenCode 会话不能弥补这条从未发送的新消息。

**方向：** 新要求采用有身份的持久化消息，记录待发送/已接收状态；恢复时不丢失，也不因重复继续而反复注入。不把“写入任务文件”当作“执行器已接收”。

### G05 · P0：设置页的模型选择没有统一驱动 OpenCode 路径

**证据：隔离配置 + 真实 CLI 参数捕获复现。**

- 在临时 home 中将本产品设置保存为 `commandcode / deepseek/deepseek-v4.1-flash`。
- 没有 runner 环境覆盖、项目也未指定模型时，OpenCode 实际 `-m` 仍是 `opendesign/deepseek-v4.1-flash`。
- `lib/runners/index.mjs:23–36` 和 `lib/runners/opencode.mjs:149` 使用自己的模型来源；设置页及 `www/panel.js:189–195` 展示的则是 `provider-settings.mjs` 选择。
- `lib/server.mjs:447–457` 的首页就绪判断仍基于旧模型配置，不能证明所选 OpenCode runner 能运行。

**影响：** 用户选择、显示和真实调用可能不一致，涉及费用、材料发往哪个渠道，以及故障排查。模型参数已复现；本轮未调用真实渠道，不能据此宣称某一把 key 实际被使用。

**方向：** 先明确一种设置语义：统一配置由适配器显式映射，或明确分开 runner 配置与模型配置。启动前生成实际执行配置快照，展示覆盖来源；凭证只暴露来源和指纹，不回显。不能靠增加文案掩盖不生效。

### G06 · P1：CLI 恢复时的任务模式可能退回 article

**证据：真实 CLI + 假 OpenCode 对照复现。**

- 原任务保存为 `topic`；普通 `ask --resume --dir ...` 生成 article 模板。
- 显式增加 `--mode topic` 后，模板才恢复正确。
- `vh.mjs:2543` 已读到 `job.mode`，但 `2570–2580` 另用命令行默认值计算模板模式。

**重要限定：** 当前网页 `chatSpawn()` 会显式传 `--mode`（`lib/server.mjs:1081`），所以不能将此结论扩大为“所有网页选题都会变成文章”。

**方向：** 模式来自同一任务契约，恢复不得用入口缺省值覆盖已保存意图。覆盖 topic、edit-copy、edit-visual 等模式的恢复测试。

### G07 · P0：发布防护未成为所有提交路径的共同事务

**证据：静态确认 + 防护函数隔离复现。**

- 单条 `submit()`（`lib/publish-api.mjs:147–164`）检查 `confirmed` 后直接提交，没有在提交入口执行 `preflight()`；预检主要依靠前端先调用。
- 批量路径（`194–205`）只阻断 cooldown，绕过 `submit()` 包装直接调用 `service.submit()`，因此未复用单条的尝试记账，也未对 unknown/duplicate 作相同处理。
- `lib/publish-guard.mjs:114–118` 先按项目过滤，再判断 rate；隔离复现为 A 项目冷却、B 项目仍允许，不是注释声称的跨项目账号冷却。
- Electron 的 `desk/main.mjs` 也直接调用发布 service；`desk/service.mjs` 的 `submitting` 仅为实例内闸门，不是跨进程账号锁。
- 尝试日志在提交返回后才写；崩溃窗口没有预先持久化的“正在提交/结果待核对”记录。损坏日志会退回空记录（`readJournal()`）；unknown 30 分钟后自动放行也不能证明没有稿件。

**影响：** 刷新、切项目、批量、另一发布进程或崩溃之后，保护语义不一致。一次界面确认不能代替未知结果核对，更不应被解释为明确授权重复投稿。

**方向：** 共同入口承担精确媒体身份、账号级互斥/冷却、尝试预写、结果记录与核对；单条、批量和 Electron 只做适配。没有平台幂等保证时，不承诺端到端 exactly-once；优先确保未知结果不被自动重发。

### G08 · P1：调度有真实断点，文件原子替换尚不足以保护业务

**证据：静态确认 + 隔离函数/交错写入复现。**

1. `scripts/schedule-daemon.mjs:108–117` 先调用 `shouldBuild()`；空队列已返回 `empty`，随后“空了就发现选题”的分支无法到达。手动 `--discover` 是另一条路径，不受此结论影响。
2. `readSchedule()` → 修改 → `writeSchedule()` 无跨进程更新保护。用两个旧快照交错写入，可复现新增选题被后一次写入覆盖。原子 rename 只避免半个 JSON，不避免丢更新。
3. 建工程后才 `attachProject()`，关联后再启动 ask；两个窗口都缺少持久化、可核对的派发事务。重叠守护进程、网页派发和崩溃恢复需要专项故障注入，不能声称已复现全部重复制作情形。
4. `dispatchedToday()` 使用 UTC 日期，而时段按本地时间；用 +08:00 同一本地日 01:00 与 10:00 的固定时间戳复现每日计数为 0，而非 1。

**方向：** 保留“执行状态从项目推导”的优点；只为队列更新和派发身份补窄事务、互斥与恢复记录，不恢复一大套重复任务状态。关联工程可携带稳定队列身份，便于恢复查找。时间规则明确时区。

**当前已有保护：** 本轮读取到的 `readSchedule()` 只在 ENOENT 时返回空队列，JSON 损坏会抛错，不能再列为“队列损坏会静默清空”。

### G09 · P1：上传没有资源上限，也没有可靠反馈与版本策略

**证据：静态确认；未做真实大文件压力试验。**

- `lib/server.mjs:432–443` 将整个上传缓存在内存，`Buffer.concat()` 两次，再同步写盘；未见请求体积、累计工程配额或中断清理保护。
- `www/panel.js` 上传也先读取完整 ArrayBuffer，失败处理没有给用户充分反馈。
- 同名素材直接写入，缺少冲突/替换约定；后续还应专项核对上传目录与目标文件链接边界。

**方向：** 流式临时写入、请求/工程/磁盘预算、明确错误和上传状态、完成后提交；同名替换需要可解释的策略。不能用降低视频画质或关闭技术保护解决。

### G10 · P1：两种 runner 返回值相似，但能力并不等价

**证据：接口与调用点静态确认；部分由 G03–G06 复现。**

- local 路径有工具级受限编辑、检查点、停滞预算、修复事务；OpenCode 的 `run()` 没有消费上层传来的 mode、automation、instructions 等字段。
- `.opencode/agents/vh-builder.md` 已有危险命令和外部目录拒绝规则，不应说完全无限制；但命令黑名单和自然语言约束不是完整沙箱，也不等价于按任务白名单限制文件/阶段。
- 当前 adapter 没有汇总 OpenCode 的用量与成本；`lib/cost.mjs` 主要读取旧 `.vh-state.json.usage`，并按固定模型价计算，不能视作新路径的完整账单。
- OpenCode 会话恢复与 local 检查点恢复不同，状态提示仍主要按本地 checkpoint 判断；不能把“接续会话”描述为已证明工具不会重复执行。
- shared 服务里工具的终止、权限/插话失败、模型用量上限及协议版本差异，尚需专门集成测试；本轮未验证真实付费任务的取消完成性。

**方向：** 显式定义 runner 能力与统一的 RunRequest/RunResult，而不是为了抽象整齐强行抹平差异。支持什么就展示什么；不支持的安全约束必须阻断或采用受控工具网关，不静默忽略。

## 六、尚未达到成熟产品的非缺陷能力

### 1. 产品控制：把“让模型猜”变成“用户可控”

- 制作 brief 缺少统一、可编辑的结构：来源、受众、要回答的问题、范围、画幅、交付目标、可选风格/声音与时长上限。
- `lib/brief.mjs` 的关键词抽取是辅助，不能承担完整需求合同。
- 应提供合理默认和少量可选项，不把每次开片变成填写长问卷；默认仍不限时长、内容优先。
- 修改前能预览范围与受影响阶段；修改后有文件/场景差异和版本对比。已有文件备份、任务归档和冲突检查可复用，不应另造互不相认的历史系统。

### 2. 成片质量：现在有规则与样片，还缺可重复的产品基线

- 结构检查、字幕检查和素材有效不等于观众听懂，也不证明配音自然、动作随讲述推进。
- 本轮没有抽样试听或重新制作真实视频，因此不对当前成片质量作打分，也不从代码推断所有视频都差。
- 建议建立离线质量回归集：文章改编、选题解释、数字比较、操作演示、长文、英文/路径多、竖屏、小范围改稿等代表场景。
- 固定来源与期望要求，观察讲述、发音、字幕、画面关系及增量修改是否守约；人工样本检查用于产品研发，不自动变成每支视频的强制审稿工序。
- 优先做少量可控的视觉/声音方案和逐场反馈，而不是继续堆特效、模板和抽象评分。

### 3. 安装维护：仍像开发者自己的环境

- `package.json` 有依赖锁定基础，但缺完整运行环境合同；Chrome 路径为 macOS 固定位置，TTS 与 skill 依赖用户目录。
- `lib/doctor.mjs` 主要检查旧模型凭证、静态环境与部分文件存在，未覆盖默认 OpenCode runner 的实际能力；已有浏览器安全策略必须保留。
- 双击启动依赖终端存活，端口探测只确认有服务响应；缺少明确的实例身份、运行版本、升级后旧服务提醒与安全重启体验。
- 需要首启自检、支持平台/版本矩阵、迁移预检、升级备份和回滚路径；不应自动覆盖未知自定义引擎。

### 4. 可观测性：日志多，不等于用户可排障

- 已有阶段耗时和部分失败分类；缺少贯通 task/attempt/session/stage/publish-attempt 的诊断关联。
- 需要在界面解释“哪个步骤失败、已有文件是否保留、继续会做什么、可能产生什么费用”。
- OpenCode 的用量无数据时显示未知；价格与余额不能硬猜，设置付费硬上限前要确认执行器是否真的可执行。
- 跨项目资源准入尚不完整。单次 render 的并发/内存预算不等于整机多工程的总预算。
- 脱敏支持包只收集必要诊断，默认不带原文、凭证、完整模型对话或用户项目代码。

### 5. 发布体验：先可靠交付，再扩平台

- 需要清楚区分“发布包已导出”“请求已提交”“平台已收稿”“审核中”“已上线”和“未知待核对”。
- 完整交付在网页应形成直接可用的出口：视频、SRT、三比例封面、标题/简介/标签/置顶评论/封面文案。
- 现有 `shouldPublish()` 和定时发布配置不能当作已接通的运行闭环；本轮未找到它在生产派发脚本中的消费者。是否保留并接通，须先明确用户授权与重启后的语义。
- 不建议此时扩更多发布平台或自动重发，先收敛共同事务。

### 6. 工程治理：代码量不是问题，边界和可验证性才是

本轮枚举：`lib/` 140 个相关代码文件约 2.42 万行，`www/` 约 4533 行，`desk/` 约 2819 行；185 个 `.test.mjs`。`vh.mjs` 3315 行，`lib/agent.mjs` 2769 行，`lib/server.mjs` 1108 行。

- 代码拆分已经不少，不能因文件长就主张重写；真正要拆的是 CLI/HTTP/runner 中重复的业务决定。
- 当前工作副本未见 `.git` 与 `.github/workflows`，不代表其他位置没有版本库；但本地尚不能据此核对发行版本与回滚基线。
- 应有稳定的版本与配置 schema、迁移策略、错误码/事件协议，以及兼容性测试。
- 185 个测试文件与本轮 79 项通过说明基础投入充足；G03–G06 仍能复现，说明测试重心未完整覆盖默认新路径的系统契约。

## 七、推荐架构收敛点

不重写渲染器，不换前端框架。围绕现有代码收敛五个共同边界：

1. **ExecutionConfig**：实际 runner、模型/渠道/端点来源、配置版本与能力；启动时解析并保存脱敏快照。
2. **TaskContract**：原始目标、模式、补充要求、允许修改范围、交付目标与可执行的预算。CLI、网页、队列只提交同一种请求。
3. **TaskCoordinator**：任务/attempt 身份、锁、执行器适配、恢复、取消和目标相关的收尾；不把这些分别留在入口里。
4. **DeliveryState**：复用已有产物凭证，分开执行结果、当前版本交付与用户认可；所有页面和队列读取同一观察结果。
5. **PublishTransaction**：账号级互斥、预检、持久化尝试、结果未知核对；网页、批量、Electron 共用。

队列是否改用 SQLite 应由写入并发和恢复需求决定。当前可以先实现窄文件事务；换数据库不自动解决幂等、授权和崩溃窗口。

## 八、分阶段开发建议与验收门槛

### 第一阶段：可信的单支制作闭环与安全底线

先写能复现问题的回归测试，再修 G01–G06；并为 G07 加上共同提交入口的最小必要保护。安全问题与状态合同一起处理，不等视觉美化完成再补。

验收：

- 预览脚本不能读写工作台控制域或借其发起危险请求；合法预览、素材加载与 `renderAt` 仍可用。
- 隐藏私有文件、符号链接越界、错误 Host/Origin 都被阻断；合法视频 Range 和下载不退化。
- 设置页展示与实际启动参数/配置来源一致；不静默切换渠道。
- 两种 runner 都覆盖 article/topic/edit/edit-copy/edit-visual/edit-script；恢复保留模式和新增要求。
- 空输出、旧片未改、缺文案、阶段失败都不会冒充当前目标完成；仅文案任务也不会被迫重渲。
- 状态在首页、项目页、队列和重启后保持一致。

### 第二阶段：连续使用与不可逆动作可靠性

补齐 G07–G10、队列事务、上传预算、整机准入及支持诊断。

验收：

- 单条/批量/Electron 共用投稿保护；A 工程风控后同账号 B 工程也受约束。
- 在提交前后断网、进程被杀、回执丢失、日志损坏时，不自动重复投稿。
- 网页与守护进程交错操作不丢选题、不会为同一派发重复建片；崩溃中间态可核对恢复。
- 空队列发现路径可达，本地日计数正确；超大上传、断连、同名冲突有确定结果。
- OpenCode 共享服务的取消和插话失败有专项集成测试，不能只测本地假进程退出。

### 第三阶段：普通用户能完成第一支，也能改好第二版

补首启自检、轻量 brief、实际配置/成本来源展示、版本差异、逐场反馈和网页交付出口；建立代表性视听回归集。

验收：由不熟悉仓库的人，从打开软件到生成、修改、下载完成代表任务，记录其卡点和需要求助的次数；不以内部开发者熟练操作替代。

### 第四阶段：可发行、可长期维护

在前三阶段稳定后补安装发行、版本迁移/回滚、持续集成、长时间多工程压力测试与平台兼容矩阵，再讨论新平台、协作或更强无人值守能力。

## 九、用哪些指标判断真的进步

先采集基线，不先编成功率、成本、耗时承诺：

- 首次使用到首个技术有效交付的成功率、制作耗时、求助次数；视频时长单独记录。
- 当前目标交付成功率，与仅执行器正常退出的比例分开。
- 继续任务成功率、新要求实际送达率、未授权重放次数。
- 只改文案/单场时的无关改动与无关重渲次数。
- 每支视频真实用量、已知费用和未知费用覆盖率。
- 发布结果未知数量、核对闭环率、重复投稿事件。
- 固定回归集的讲述/发音/字幕/画面问题数量，以及修好这些问题需要几轮。

## 十、建议现在先作的决策

**先把映序做成可信的单机制作产品，而不是继续增加功能面。第一批聚焦“实际配置—用户要求—执行—交付”贯通，并收紧预览/静态文件/发布的安全边界。**

暂不建议：重写前端、换技术栈、增加强制审稿、扩发布平台、做团队账户系统，或用更多自动重试掩盖状态不一致。下一轮开发范围应在确认优先级后再开始。
